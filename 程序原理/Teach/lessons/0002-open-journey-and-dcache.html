从第一课结束的地方开始

第一课我们认识了 VFS 的四大对象：超级块、inode、dentry、file，以及它们之间的基本关系。

但当时留下的问题是：一次 open() 从用户态到磁盘，到底经过了哪些步骤？dcache 在其中究竟做了什么？

这就是本课要回答的。

1. open("doc.txt", O_RDONLY) — 九步全景

下面的九步从用户态出发，经过系统调用入口、VFS 通用层、具体文件系统，直达磁盘。每一步都标注了内核源码的对应文件路径。

第 1 步：glibc 包装（用户态 → 陷入内核）

用户程序调用 open("doc.txt", O_RDONLY)，实际上是调用 glibc 中的包装函数。包装函数将参数存入寄存器（x86‑64：rdi=路径，rsi=flags，rdx=mode），然后执行 syscall 指令，切换到内核态。

glibc/sysdeps/unix/sysv/linux/openat.c

第 2 步：syscall 入口（架构相关）

内核从 MSR_LSTAR 读取系统调用入口地址，进入 entry_SYSCALL_64()。保存寄存器，调用 do_syscall_64()。根据 rax 中的系统调用号（257 = __NR_openat），从 sys_call_table 找到对应的处理函数。

arch/x86/entry/entry_64.S → arch/x86/entry/common.c

第 3 步：VFS 通用入口

do_sys_open() 是真正的 C 入口。它把用户态路径字符串拷贝到内核空间，然后调用 do_filp_open() 进行真正的文件打开工作。

fs/open.c — do_sys_open() → do_filp_open()

第 4 步：路径解析（最复杂的一步）

path_openat() → link_path_walk()。这是整个 open() 中最核心也最复杂的部分。如果路径有 N 个分量，这一步就会重复 N 次（见第 4a–4e 子步骤）。

以 /home/user/doc.txt 为例，内核会依次解析 / → home → user → doc.txt。

fs/namei.c — 路径解析的核心代码都在这个文件中

🔽 展开第 4 步的 5 个子步骤
4a. 获取起始点

从当前进程的 fs->pwd（当前工作目录）拿到起始 dentry。如果是绝对路径（以 / 开头），则从 current->fs->root 拿到根 dentry。根目录的 dentry 永远不会被 dcache 换出。

4b. dcache 查找（lookup_fast()）

先在 dcache 中查找当前路径分量的 dentry。dcache 的内部结构是 哈希表（不是树），哈希键是 (父 dentry 指针 + 分量名字符串 hash)。

如果命中 → 直接拿到 dentry → 拿到 inode → 零次磁盘 I/O。如果未命中 → 走下一步。

fs/namei.c — lookup_fast() → __d_lookup_rcu()

4c. dcache 未命中 → 磁盘 I/O（lookup_slow()）

VFS 调用父目录 inode 的 i_op->lookup()。对于 ext4：

  1. 读取父目录文件的数据块（磁盘 I/O）
  2. 在目录项列表中搜索当前分量名
  3. 找到后拿到目标 inode 号
  4. ext4_iget() 从磁盘 inode 表读取 inode 数据（磁盘 I/O）
  5. 用 d_add() 创建新 dentry，挂入 dcache 哈希表

fs/ext4/namei.c — ext4_lookup() → ext4_iget() (fs/ext4/inode.c)

4d. 检查软链接

如果查到的 inode 类型是 S_IFLNK（软链接），则调用 pick_link() → i_op->follow_link()，读取软链接的内容作为新路径，回到步骤 4a 重新解析。

这就是软链接可以"跨文件系统"的根本原因——它存的是路径字符串，每次使用时才重新 lookup。

4e. 返回最终 dentry

所有分量解析完成后，返回目标文件/目录的 dentry 和 inode，封装在 struct path 中。

第 5 步：权限检查

may_open() → inode_permission()。检查进程的 uid/gid 是否匹配 inode 的 i_uid/i_gid，请求的读写模式是否与 i_mode 权限位冲突（包括 ACL、SELinux 等扩展权限检查）。

fs/namei.c — may_open()；fs/posix_acl.c — ACL 检查

第 6 步：分配 file 对象

alloc_empty_file() 从 slab 分配器分配一个新的 struct file，初始化关键字段：

  • f_path = dentry + mount 信息
  • f_op = inode 的 i_fop（默认文件操作函数表）
  • f_mode = O_RDONLY
  • f_pos = 0

fs/file_table.c — alloc_empty_file()

第 7 步：调用具体文件系统的 open()

do_dentry_open() → f_op->open()。大部分普通文件系统（ext4、XFS 等）的 open 方法为 NULL（不需要额外操作）。设备文件比较特殊——此步骤会替换 f_op 为设备驱动的 file_operations。

fs/open.c — do_dentry_open()

第 8 步：分配文件描述符

get_unused_fd_flags() 在进程的 fdtable 中找到最小的未用 fd 编号（current->files->fdt），设置对应位图标志。

fs/file.c — get_unused_fd_flags()

第 9 步：关联 fd → file，返回

fd_install(fd, file) 将 file 指针写入 current->files->fdt->fd[fd]。返回 fd 编号给用户态。完成！用户拿到了一个整数 fd，背后是一条完整的引用链：

  task_struct → files_struct → fdtable → fd[3] → file → dentry → inode → super_block

fs/file.c — fd_install()

一次 open 的关键数据流（可视化）

2. dcache 深度解析

上一课介绍了 dentry 的基本概念。这里我们深入它的内部实现，回答你在学习中提出的那些问题。

2.1 dcache 的哈希表结构（不是树！）

dentry 在逻辑上构成了树（父子关系通过 d_parent、d_subdirs 指针维护），但 查找用的是哈希表，不是树遍历。

// 全局哈希表 — 32768 个桶
#define D_HASH_BITS  15
static struct hlist_bl_head dentry_hashtable[1 << D_HASH_BITS];

// 哈希键的计算方式：
// hash = hash(parent_dentry_pointer, d_name.string)
// 注意：是全路径的每个分量独立哈希，不是整个人"/home/user/doc.txt"

2.2 查找过程：快速路径 vs 慢速路径

lookup_fast() 使用 RCU（Read-Copy-Update）无锁读来尝试从 dcache 中获取 dentry。这是 dcache 的性能核心——大部分查找在 RCU 路径就能命中，不需要拿任何锁。

// fs/namei.c — lookup_fast() 简化逻辑
struct dentry *lookup_fast(struct nameidata *nd)
{
    // 快速路径：RCU 无锁读
    dentry = __d_lookup_rcu(parent, &nd->last, &nd->seq);
    if (dentry)
        goto success;

    // 慢速路径：拿锁再查
    dentry = __d_lookup(parent, &nd->last);
    if (dentry)
        goto success;

    // 未命中 → 走磁盘 I/O
    return NULL;

success:
    // 验证 inode 是否还在（有可能被 evict 了）
    if (unlikely(!dentry->d_inode))
        return NULL;
    return dentry;
}

为什么用 RCU？因为路径解析是文件系统最高频的操作——每次 open()、stat()、readdir() 都会触发。如果每层都拿锁，多线程并发时锁竞争会剧烈拉低性能。RCU 允许读者在完全不拿锁的情况下读取 dcache，只有当检测到并发修改时才退回到锁保护路径。

2.3 负缓存（Negative Dentry）

当 open() 一个不存在的路径时，内核并不会"查过就算了"——它把"不存在"也缓存下来：

// dcache 中的"负 dentry"
dentry "nonexistent"  →  d_inode = NULL
                         d_flags  |= DCACHE_MISS_TYPE

下次再查同一个路径，lookup_fast() 看到 d_inode == NULL→ 直接返回 -ENOENT，完全不需要再走磁盘。

💡 为什么要缓存"不存在"？想象你编译程序时，gcc 会到多个 include 路径搜索头文件：/usr/local/include/stdio.h → 不存在 → /usr/include/stdio.h → 找到了。没有负缓存，每次编译都要读三四个目录的数据块来确认文件确实不存在。负缓存让这个开销降为零。

你问过的一个好问题：负缓存会被大量无用查询撑爆吗？

会。内核的应对：

  1. LRU 回收时优先回收负 dentry——代码在 fs/dcache.c 的 dentry_lru_isolate() 中对 d_inode == NULL 的 dentry 给予更高的回收优先级
  2. 内存压力下缩水器（shrink_slab）会整体扫描 dcache 并驱逐最多最旧的条目
  3. 真实攻击案例：CVE-2018-5390 利用了大量畸形 TCP 包触发内核路径解析，产生大量负 dentry。后续内核增加了更激进的负 dentry 回收。

2.4 dentry 如何"钉住" inode（正确性担保）

这是你问过的最核心的问题：dentry 和 inode 是两个独立对象，怎么保证 dentry 存在时 inode 不会消失？

答案就在 d_add() 中：

// fs/dcache.c
void d_add(struct dentry *dentry, struct inode *inode)
{
    dentry->d_inode = inode;          // dentry 指向 inode
    if (inode) {
        spin_lock(&inode->i_lock);
        atomic_inc(&inode->i_count);  // ← 关键：inode 引用计数 +1！
        spin_unlock(&inode->i_lock);
    }
    d_rehash(dentry);                 // 挂入哈希表，可被 lookup 命中
}

所以担保链是：

dentry 在哈希表中  ⇒  dentry->d_inode != NULL  ⇒  inode->i_count >= 1  ⇒  inode 不会被 evict

反过来，要释放 inode 的条件是：

inode 释放 = (i_nlink == 0)  且  (i_count == 0)
              ↑ 磁盘上没有目录项指向它    ↑ 内存中没有 dentry/file 引用它

2.5 删除场景推演：理解 i_nlink 和 i_count

把之前课堂对话中的场景整理成一条时间线：

初始 /tmp/test.txt → inode #42，i_nlink=1，i_count=0（尚未被任何人打开）
open() lookup 创建 dentry → d_add() → i_count = 1（dentry 钉住了 inode）
ln /tmp/hard.txt 第二个 dentry 创建 → d_add() → i_nlink = 2，i_count = 2
rm /tmp/test.txt vfs_unlink() → ext4_unlink()（删除目录项）→ i_nlink = 1
d_delete() → 从哈希表摘除 dentry → iput() → i_count = 1
👉 inode 还在！ 因为 hard.txt 的 dentry 还引用着它
rm /tmp/hard.txt vfs_unlink() → i_nlink = 0
d_delete() → iput() → i_count = 0
👉 inode 释放！ 数据块标记为空闲

这就是"文件删了但空间没释放"的根本原因：被删的文件如果有进程打开了（持有 fd），i_nlink = 0 但 i_count > 0，inode 和数据块都不会被回收。重启后所有 fd 释放了，空间才回收。

2.6 dcache 的内存回收机制

dcache 不是无限增长的。内核通过几个机制控制它的内存占用：

机制触发条件行为
LRU 链表回收 系统内存低于 watermark 从 dentry 的 LRU 链表尾部开始回收，优先回收：
  • 负 dentry（d_inode == NULL）
  • 未被打开的 dentry（i_count == 0 但 dcache 还保留）
shrink_slab 内核内存压力到达 /proc/sys/vm/ 阈值 遍历所有 slab 缓存（包括 dentry、inode），缩水到目标值
dentry_unhash / d_prune 文件被删除 从 dcache 哈希表摘除，断开与 inode 的连接

你可以通过以下命令观察 dcache 的使用状况：

# 查看 dentry 状态：nr_dentry / nr_unused / age_limit / want_pages
cat /proc/sys/fs/dentry-state
# 输出示例：47052  44532  45      0       0       0
# 第1列：当前 dentry 总数
# 第2列：未使用的 dentry 数（d_count==0 但还在 dcache 中备用）
# 第3列：回收年龄阈值（秒）

# 查看 slab 分配器中的 dentry 和 inode 缓存
grep -E "(dentry|inode)" /proc/slabinfo

3. 知识测验

1️⃣ lookup_fast() 查找 dcache 时，用的是什么数据结构？
正确答案：C
哈希键是 (父 dentry 指针 + 名字 hash)。这让人迷惑的一点是 dentry 的逻辑关系看起来像树，但查找入口是哈希表——O(1) 时间复杂度。
2️⃣ 执行 rm test.log 后，为什么可能空间没释放？请选出必要条件。
正确答案：A
选项 A 中，tail -f 持有 fd → file 对象 → inode 的引用 → i_count > 0，即使 i_nlink==0 也不会释放空间。
选项 B 不对：有硬链接时 i_nlink 不会变成 0，所以空间本来就不该释放——这不是"释放不了"的问题。
选项 C：负缓存是"不存在"的记录，不影响已存在的文件。
关键判断标准：要空间不释放，必须是 i_count > 0 且 i_nlink == 0 同时成立。只有 A 对。
3️⃣ 关于 dcache 的负缓存（negative dentry），下面哪项描述是正确的？
正确答案：C
负缓存纯在内存（A×），LRU 会优先回收它们（B×），而且负缓存产生不需要磁盘 I/O（D×）。C 正确描述了它的优势（加速不存在判断）和代价（可能被攻击者利用来挤占 dcache）。
