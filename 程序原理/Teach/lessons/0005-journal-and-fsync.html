从 delalloc 的"阿喀琉斯之踵"说起

第四课我们学习了 delalloc——把磁盘块分配推迟到回写时，将多次小写入合并为一次大的连续分配。但这也带来了一个风险：

⚠️ delalloc 的代价

write() 返回成功时数据只在 page cache 中。如果回写前系统崩溃——数据彻底丢失。但这只是问题的一角。

即使没有 delalloc，传统的文件系统写入也存在一个根本问题：多步操作不是原子的。

写入一个文件需要更新至少三处磁盘数据：
  ① 数据块内容本身
  ② inode 中的元数据（大小、时间戳、extent 树/块指针）
  ③ 块位图（标记这些块已被占用）

如果写完①，还没来得及写②③就崩溃了：
  → 重启后：数据块里有内容，但 inode 不知道它。
  → 这些块在 bitmap 中仍标记为"空闲"，可能被其他文件覆盖。
  → 结果：文件内容损坏或交叉链接。
💡 核心问题：磁盘的写入是"扇区级原子"的——一个扇区（512 字节）的写入要么完成要么没完成。但文件系统的更新涉及多个扇区、多个块，不是原子的。系统在中间任何一个时刻崩溃，磁盘状态都会不一致。

1. JBD2：ext4 的日志层

ext4 引入了 JBD2（Journaling Block Device layer 2）——这是一个独立的日志层，不仅 ext4 用，也在 ocfs2 等其他文件系统中使用。它的核心思想是：在修改磁盘数据之前，先把"你要做什么"记到日志里。

1.1 日志的物理位置

ext4 格式化时会在磁盘上预留一段空间作为日志（journal）。默认情况下，日志内嵌在文件系统内部（journal_internal），也可以放在外部块设备上（用于高性能场景）：

查看你的日志参数：

# Journal inode:            8
# Journal size:             128M
# Journal backup:           inode blocks

2. JBD2 的事务模型

JBD2 的核心概念是事务（transaction）。一个事务包含一组"要么全部生效、要么全部不生效"的磁盘更新。

2.1 三要素：句柄（handle）→ 事务（transaction）→ 提交（commit）

开始事务

内核线程调用 journal_start() 获取一个 handle（句柄）。句柄是文件系统代码与 JBD2 之间的接口——每个需要修改元数据的操作都要先拿一个 handle。

// 简化示例：ext4 写入一个数据块时的日志操作
handle_t *handle = ext4_journal_start(inode, 1);  // 申请一个句柄
if (IS_ERR(handle))
    return PTR_ERR(handle);

// 在日志中预留空间
ext4_journal_get_write_access(handle, bh);  // 通知 JBD2 要修改这个 buffer head

ext4_mark_inode_dirty(handle, inode);       // 修改 inode
ext4_journal_dirty_meta(handle, bh);        // 标记 buffer 为脏
提交事务（commit）

journal_stop(handle) 释放句柄。当所有活跃句柄都停止后，JBD2 将该事务提交到磁盘日志区：

journal_stop(handle);
// 内核在适当时机自动触发提交，或 fsync() 主动触发
Checkpoint（回收日志空间）

事务提交后，日志中已经记录了本次修改。但日志空间是有限的，需要把日志中的数据真正写到目标位置（inode 表、数据块等），然后才能释放日志空间。

// Checkpoint 完成 = 日志中的修改已同步到目标位置
// 此时这些日志块可以回收，给新事务使用

2.2 一次完整的日志提交过程

🚀 事务提交的五个步骤
  1. 锁定事务：禁止新的句柄加入，等待所有正在进行的句柄完成
  2. 写描述块：写一个 descriptor block，记录本事务中所有要修改的块号及其校验和
  3. 写数据块：将所有被修改的块（元数据块）写入日志区域。可以合并多个块到一次 I/O
  4. 写提交块：写一个 commit block，包含事务ID（TID）、校验和等。这一步代表事务"已提交"的原子设施
  5. 唤醒等待者：通知等待该事务完成的进程（如 fsync 的调用者）

一个关键设计：第 2~3 步写日志块，第 4 步写提交块。如果在写提交块之前崩溃——重启后检查日志时发现没有提交块，会丢弃这个不完整的事务（认为它从未发生过）。

2.4 崩溃恢复——回放日志

系统崩溃重启后，在挂载文件系统时，e2fsck 或 JBD2 的恢复机制会检查日志：

🔁 恢复过程
  1. 扫描 journal 区域，找到完整的已提交事务（有描述块 + 数据 + 提交块的）
  2. 对于每个完整事务：把日志中的数据回放（replay）到目标位置（inode 表、块位图等）
  3. 对于不完整的事务（有描述块但没有对应的提交块）：直接丢弃——认为从未发生过
  4. 回放完成后，文件系统状态与崩溃前一致——所有已提交的修改都已恢复
💡 关键原则：日志不保证"崩溃时不丢数据"，它保证的是文件系统的一致性。要么修改全部完成（事务已提交），要么全部没发生（事务未提交或丢弃）。这是 ACID 中的 A（原子性）和 C（一致性）。

3. ext4 三种日志模式

ext4 提供了三种日志模式，通过 mount -o data=... 选项设置：

模式mount 选项谁被日志化性能安全性
ordered（默认） data=ordered ✅ 元数据记录日志
✅ 数据先于元数据写盘		 ⭐⭐⭐⭐ ⭐⭐⭐⭐
writeback data=writeback ✅ 元数据记录日志
❌ 数据不记录日志
❌ 数据和元数据顺序无保证		 ⭐⭐⭐⭐⭐ ⭐⭐
journal data=journal ✅ 元数据记录日志
✅ 数据也记录日志（写两次：先日志，再目标位置）		 ⭐⭐ ⭐⭐⭐⭐⭐

3.1 data=ordered 默认模式

这是 ext4 的默认模式，也是绝大多数 Linux 发行版的默认选项。它的规则是：

① 数据块（文件内容）写入目标位置 ✅（直接写，不进日志）
② 元数据（inode、bitmap 等）写入日志 ✅
③ 顺序保证：① 必须在 ② 之前完成

为什么数据先写？考虑这个场景：

追加写 4KB 到文件末尾：
  数据块（新内容）→ 直接写到数据区 ✓（先做）
  inode 更新（新的 i_size、extent 指针）→ 写到日志 ✓（后做）

如果在这两步之间崩溃又恢复：
  ➡️ 数据块已经写好了
  ➡️ 日志中的 inode 更新被回放到目标位置
  ➡️ 文件系统一致 ✅

反过来如果元数据先写、数据后写：
  ➡️ inode 已经记录了"文件有 4KB 新数据"
  ➡️ 但数据块还没写就崩溃了
  ➡️ 重启后 inode 指向了"全零"的数据块 ➡️ 文件内容全零 ❌
  （这就是 known as "torn write" 的一种表现）

3.2 data=writeback 模式

只对元数据做日志，数据直接写目标位置，不保证顺序：

writeback 模式：
  数据块 → 随时写（可能在元数据之前、之后、或同时）
  元数据 → 写日志

如果崩溃：
  元数据通过日志恢复 → 文件系统结构一致 ✅
  但文件内容可能包含"垃圾"（inode 指向了尚未写入的数据块）❌

适用场景：性能敏感、可以容忍少量文件内容损坏的系统（如某些大数据集群的临时数据）。性能比 ordered 模式高出约 5–10%。

3.3 data=journal 模式

最安全的模式——所有数据先写日志，再写目标位置：

data=journal 模式下的写入流程：

  write() → page cache → 标记脏
                  ↓
  flusher/fsync → ① 数据 + 元数据 → 写入日志
                  ② 日志提交（写提交块）
                  ③ 数据从日志回放到目标位置（checkpoint）
                  ④ 日志空间回收

这意味着每个数据块被写两次：一次进日志，一次进目标位置。性能大幅下降，但提供了最高级别的保护——即使崩溃发生在数据写到目标位置的瞬间，重启恢复时也能从日志中重放。而且 data=journal 还有一个额外的好处：不需要 fsync 就能保证数据安全——只要日志提交了，崩溃恢复时数据会自动回放。

3.4 三种模式的对比

ordered ✅

  • 数据直接写目标位置
  • 元数据写日志
  • 写顺序保证：数据先于元数据
  • 崩溃时：文件内容不会出现"零"
  • 默认模式，适合绝大多数场景

writeback ⚡

  • 数据直接写目标位置
  • 元数据写日志
  • 写顺序不保证
  • 崩溃时：文件可能含垃圾数据
  • 性能最高，安全性最低

journal 🛡️

  • 数据先写日志，再写目标位置
  • 元数据写日志
  • 数据写了两次
  • 崩溃时：可完全恢复
  • 性能最低，安全性最高

4. fsync 与 fdatasync

现在我们来回答一个实际问题："调用 fsync 后，数据到底什么时候真正在磁盘上？"

4.1 fsync() 干了什么

// 用户态
#include <unistd.h>

write(fd, buf, 4096);   // 数据在 page cache 中
fsync(fd);              // 等待所有数据刷新到磁盘

// 返回后 → 数据的耐久性有保证

在 ext4 中，fsync() 的内核路径大致是：

sys_fsync(fd)
  → vfs_fsync(file, 0)
    → ext4_sync_file(file, 0)
      → filemap_write_and_wait_range(inode)      // ① 刷脏页到磁盘
      → jbd2_complete_transaction(inode->i_journal) // ② 等待当前事务提交
      → blkdev_issue_flush(bdev)                    // ③ 发 FLUSH CACHE 命令

三个关键步骤：

① 刷脏页

filemap_write_and_wait_range() 回写该文件在 page cache 中的所有脏页。在 ordered 模式下，这就是把数据块直接写到目标位置（数据区）。

② 等待日志提交完成

jbd2_complete_transaction() 确保包含该文件 inode/bitmap 更新的日志事务已经提交到磁盘日志区。在 ordered 模式下，这一步发生在脏页刷完以后。

③ 发出 FLUSH CACHE 命令

blkdev_issue_flush() 向磁盘发送 FLUSH CACHE 命令。现代磁盘都有写缓存（write cache）——磁盘告诉"写入完成"时数据可能还在磁盘的 DRAM 缓存里，没到盘片上。FLUSH CACHE 强制把缓存中的数据刷到持久介质。

💡 关键细节：步骤 ③ 是很多工程师忽略的。即使数据写到了磁盘，也可能卡在磁盘的写缓存中。如果此时断电，磁盘写缓存中的数据仍然会丢失。这也是为什么数据库服务器通常建议关闭磁盘写缓存：hdparm -W 0 /dev/sda。或者通过 mount 选项 barrier=1 让 ext4 在日志提交时也发 FLUSH CACHE。

4.2 fsync vs fdatasync

函数同步内容同步元数据场景
fsync(fd) 数据 + 所有元数据 ✅ size、atime、mtime、ctime、权限等 关键文件、数据库 WAL
fdatasync(fd) 数据 + "必要"的元数据 ⚠️ 只同步后续读取所必需的元数据（主要是文件大小 i_size） 日志文件、高性能场景

fdatasync 的优化点：当你只追加写日志，不修改文件权限/所有者的场景，fdatasync 可能少刷一些元数据。但注意：如果文件大小变了（追加写），i_size 是"后续读取必需的"，所以它仍然会被同步。实际性能差异通常不大。

4.3 O_SYNC / O_DSYNC

如果你每次 write() 都要同步，可以在 open() 时传 O_SYNC：

fd = open("file.txt", O_WRONLY | O_SYNC);
write(fd, buf1, 4096);  // 隐式包含 fsync 语义
write(fd, buf2, 4096);  // 每次 write 都做一次 fsync

但每次 write 都 fsync 性能极差。现实中通常的做法是：关闭 O_SYNC，在关键时间点手动调用 fsync()，这样可以在批量写入后一次同步。

// 差
fd = open("file", O_WRONLY | O_SYNC);
write(...);  // 每次都 flush
write(...);
write(...);

// 好
fd = open("file", O_WRONLY);
write(...);
write(...);
write(...);
fsync(fd);   // 一次 flush 所有

5. 全景回顾：一次带日志的完整写入

将第四课的 read() 六层全景和第五课的日志机制合一，看看一次 write() + fsync() 的完整路径：

第 1 层：write() 系统调用

write(fd, buf, 4096) → vfs_write() → ext4_file_write_iter()

第 2 层：写入 page cache

generic_perform_write() → 分配/获取 folio → copy_page_from_iter()（用户数据→内核页框） → mark_buffer_dirty() 标记脏

如果在 data=journal 模式下，这一步还要通过 journal_start() 预留日志空间。

第 3 层（如果调用 fsync）：刷脏页 → 数据到磁盘

filemap_write_and_wait_range() → ext4_writepages() → mpage_submit_folio() → 构造 BIO → 提交到块层

数据块直接写目标位置（ordered 模式）

第 4 层（数据刷完后）：日志提交

延迟分配的磁盘块在 writepages 中分配 → inode 更新（extent 树、i_size） → 通过 journal_stop() 触发 JBD2 事务提交

事务写入日志区：描述块 → 元数据块 → 提交块

第 5 层：FLUSH CACHE 命令

blkdev_issue_flush() → 发给磁盘 → 磁盘写缓存中的数据刷到盘片

第 6 层：fsync() 返回

所有步骤完成后，fsync() 返回 0。此时数据已安全到达磁盘持久介质。

6. 知识测验

1️⃣ JBD2 为什么需要"提交块（commit block）"？
正确答案：B
提交块是事务的"原子提交标记"。只有写入了提交块，恢复时才会回放该事务的数据。如果在写描述块之后就崩溃了，没有提交块 → 被认为是"不完整事务" → 直接丢弃。这就是"原子性"的保障机制。
2️⃣ ext4 默认的日志模式 data=ordered 的核心保证是什么？
正确答案：C
ordered 模式的核心：数据块直接写到目标位置（不经过日志），但必须在元数据日志提交之前完成。这保证了即使崩溃后重放日志，inode 指向的数据块一定是已经写好的——不会出现"文件有数据但全是零"的情况。
3️⃣ fsync() 在内核中做了哪三件事？
正确答案：B
fsync 的三步：① filemap_write_and_wait_range() 刷脏页到数据区；② jbd2_complete_transaction() 等待包含元数据的日志事务提交完成；③ blkdev_issue_flush() 发 FLUSH CACHE 命令穿透磁盘写缓存。三步缺一不可。
4️⃣ fdatasync() 相比 fsync() 可能少同步什么？
正确答案：A
fdatasync() 只保证"后续数据读取所需的信息"已落盘。如果文件大小没变（只是覆盖写已有位置），某些元数据（如 atime）可以不刷。但如果文件大小变了（追加写），i_size 是必需的，所以仍然会被同步。实际性能差异通常不大。
5️⃣ data=journal 模式下，为什么每个数据块被写两次？
正确答案：B
data=journal 模式把所有数据先写入日志区域。事务提交后，JBD2 再从日志区域把数据回放到目标位置。这意味着在没有 checkpoint 完成时，数据在日志中已有备份——崩溃恢复时可以重放。代价就是每个数据块被写两次，吞吐量大幅下降。
