为什么先学 VFS？

你已经学过了 编译 → 链接 → 装载 → 内存管理 → 进程 → 系统调用 这条完整的程序执行链路。但是一个关键拼图一直缺失：文件是程序读写的最终对象。

open("hello.txt", O_RDONLY) → read(fd, buf, 4096) 这个看似简单的调用，背后从用户态到磁盘磁道的路径有多长？VFS 就是这条路径的第一站。

面试中经常会问："Linux 支持几十种文件系统（ext4、XFS、NTFS、procfs……），系统调用却只有一套，内核是怎么做到的？"

答案就是 VFS（Virtual File System，虚拟文件系统）。

1. 什么是 VFS？

VFS 是 Linux 内核中一个 软件抽象层。它定义了一套标准的接口契约，让不同的具体文件系统可以在底层自由实现，而上层的系统调用（open、read、write、stat）完全不用关心底层是谁。

你可以把 VFS 想象成 USB-C 接口：

  • 你的电脑（用户态程序）只需要知道 USB-C（VFS 系统调用）
  • 不同的设备（ext4、NTFS、procfs）各自实现了 USB-C 协议（VFS 接口）
  • 插上就能用，无需关心设备内部的具体电路

VFS 的核心思想是 面向对象设计（在 C 语言中通过结构体+函数指针实现）。它定义了四个主要的对象类型：

2. 四个核心对象

VFS 基于四个核心的 struct 构建。你可以把它们想象成文件系统世界的"四大天王"：

① 超级块（Superblock） — "文件系统实例的身份证明"

生命周期：挂载时创建，卸载时销毁。

每个已挂载的文件系统都有一个超级块。它记录了这个文件系统的全局元数据：

  • 设备信息（在哪个块设备上）
  • 操作函数表（super_operations）
  • 指向根目录 inode 的指针
  • 文件系统类型（ext4、XFS 等）

类比：超级块就像是这个文件系统的"护照"——内核通过它知道如何与这个文件系统打交道。

struct super_block {
    dev_t                      s_dev;          // 设备 ID
    unsigned long              s_blocksize;    // 块大小（字节）
    struct super_operations    *s_op;          // 超级块操作函数表
    struct dentry              *s_root;        // 根目录 dentry
    struct list_head           s_inodes;       // 所有 inode 的链表
    struct file_system_type    *s_type;        // 文件系统类型
    // ... （还有很多字段）
};

② inode（索引节点） — "对象的身份证"

生命周期：文件被访问时从磁盘读取/创建，最后一个引用释放时销毁。

inode 表示文件系统中的一个对象——可以是文件、目录、设备节点、FIFO（命名管道）或 socket。它不包含文件名！每个 inode 有唯一的 inode 号。

inode 中存储：

  • 文件类型和权限（mode）
  • 文件大小、时间戳（atime/mtime/ctime）
  • 链接计数（i_nlink）——有多少个文件名指向这个 inode
  • 数据块指针（直接、间接、extent 等）
  • 操作函数表（inode_operations）

关键洞察：你知道 task_struct 是进程的"身份证"吗？inode 在文件系统里的地位就和 task_struct 在进程管理里的地位一样——它是每个对象的唯一代表。

struct inode {
    umode_t                    i_mode;       // 文件类型 + 权限位
    uid_t                      i_uid;        // 所有者 UID
    loff_t                     i_size;       // 文件大小（字节）
    struct timespec64          i_atime;      // 最后访问时间
    struct inode_operations    *i_op;        // inode 操作函数表
    struct super_block         *i_sb;        // 所属超级块
    struct address_space       *i_mapping;   // 页缓存映射（重要！）
    atomic_t                   i_nlink;      // 硬链接计数
    // ...
};

③ dentry（目录项） — "路径名 → inode 的翻译器"

生命周期：仅在内存中存在，从不写入磁盘。由 dcache（目录项缓存）管理。

这是四个对象中最容易被误解的一个。 dentry ≠ 磁盘上的目录项。它是内核在解析路径名时，在内存中创建的"路径分量缓存"。

当你访问 /home/user/doc.txt 时，内核会创建四个 dentry 节点： / → home → user → doc.txt。每个 dentry 指向一个 inode。

为什么要搞个 dentry？ 因为每次解析路径都读磁盘太慢了。dcache 把最近用过的路径名 → inode 映射留在内存里，下一次直接命中。

struct dentry {
    struct qstr                d_name;       // 路径分量名（如 "doc.txt"）
    struct inode               *d_inode;     // 指向的 inode
    struct dentry              *d_parent;    // 父目录的 dentry
    struct list_head           d_child;      // 兄弟 dentry 链表
    struct dentry_operations   *d_op;        // 自定义操作
    // ...
};

④ file（文件对象） — "进程视角的打开文件"

生命周期：open() 时创建，close() 时销毁。

每个调用 open() 的进程都会获得一个独立的 file 结构体。它记录的是"这次打开"的上下文：

  • 当前的读写偏移量（f_pos）
  • 打开模式（只读、写、追加等）
  • 指向 dentry 的指针
  • 操作函数表（file_operations）

关键点：两个进程分别打开同一个文件 → 两个 file 对象，但共享同一个 dentry 和 inode。各自的 f_pos 独立，互不影响。

struct file {
    struct path                f_path;       // dentry + mount 点的封装
    loff_t                     f_pos;        // 当前读写偏移量
    fmode_t                    f_mode;       // 打开模式（FMODE_READ / FMODE_WRITE）
    struct file_operations     *f_op;        // 文件操作函数表
    void                       *private_data; // 文件系统私有数据
    // ...
};

3. 四个对象的关系：一次 open() 的完整旅程

把四个对象串联起来，就是一次 open() 的完整故事：

小结流程：

  1. 路径解析：VFS 从当前目录或根目录开始，逐个分量查找路径名。先去 dcache 中查找是否已经缓存了对应的 dentry。
  2. dentry 命中或创建：如果在 dcache 中没有找到，VFS 会调用父目录 inode 的 lookup() 方法去磁盘上查找，然后创建新的 dentry 并缓存起来。
  3. 获取 inode：dentry 获得了目标 inode 的引用，inode 的数据（权限、大小、块指针）现在驻留在内存中。
  4. 创建 file 对象：内核分配一个 file 结构，初始化 f_pos = 0，设置 f_op 为 inode 定义的默认文件操作函数表。
  5. 分配文件描述符：将 file 对象挂入进程的文件描述符表（fdtable），返回 fd 编号给用户态。
💡 重要的设计思想：dentry 将"文件名解析"和"文件元数据"解耦了。即使 inode 不在内存中（被回收了），dentry 结构仍然可以存在 dcache 中——下次访问如果 inode 不在了，需要重新从磁盘加载，但路径解析的结果（目录层次）可以复用。

4. 四个对象的生命周期对比

对象 生命周期起点 生命周期终点 是否持久化到磁盘
super_block mount 时创建 umount 时销毁 元数据在磁盘上有副本（超级块区域）
inode 首次访问时从磁盘加载 链接计数归零且无引用时销毁 ✅ 是（存储在 inode 表中）
dentry 路径解析时创建 内存压力下被 dcache 回收，或 inode 释放时 ❌ 否（纯内存结构）
file open() 时创建 close() 时销毁 ❌ 否（进程上下文）

5. 面试高频：这些概念能回答什么问题？

❓ 面试题："文件删除后，df 看到的空间没有释放，为什么？"

因为 inode 的 链接计数（i_nlink） 原理：

  • unlink() 或 rm 删除的只是"文件名 → inode"的映射（也就是 dentry）
  • inode 的 i_nlink 减 1，但是如果还有进程打开了这个文件，file 对象持有 inode 的引用，inode 不会被销毁
  • 只有当 i_nlink == 0 且 没有进程持有该 inode 引用时，inode 和数据块才真正被释放

原理：在 inode 结构中：atomic_t i_nlink 表示硬链接数，atomic_t i_count 表示内存中的引用数。两个都归零才是真正的释放。这就是为什么你删了一个正在被写入的日志文件，空间没释放——等持有该文件的进程关掉 fd 才行。

❓ 面试题："硬链接和软链接的区别，从 VFS 角度怎么说？"

硬链接：两个不同的 dentry 指向同一个 inode。i_nlink = 2，删除其中一个 dentry 只会让 i_nlink 减到 1，数据还在。

软链接：一个独立的 inode（类型为 S_IFLNK），它的"文件内容"是另一个路径名（字符串）。VFS 在路径解析时如果发现 dentry 指向的是一个软链接的 inode，就会调用 page_follow_link() 跳转到目标路径重新解析。

VFS 层面的本质区别：硬链接是多个 dentry → 同一个 inode；软链接是一个 inode → 存着另一个路径的字符串 → VFS 帮你重定向。

6. 技能练习：亲手验证

📝 练习 1：在终端中运行以下命令，观察结果并思考
# 查看文件 inode 号
touch test.txt
ls -li test.txt
# 输出示例：1065432 -rw-r--r-- 1 user user 0 Jun 23 10:00 test.txt
# 第一列就是 inode 号

# 查看硬链接
ln test.txt link.txt
ls -li test.txt link.txt
# 观察：两个文件 inode 号相同，链接数变为 2

# 查看软链接
ln -s test.txt soft.txt
ls -li test.txt soft.txt
# 观察：soft.txt 的 inode 号不同，类型是 l，大小是路径字符串的长度
🔍 展开思考题答案
  • ls -li 的第一列就是 inode 号
  • 硬链接：inode 号相同，链接数 = 2，两个文件名只是同一个 inode 的两个 dentry
  • 软链接：独立的 inode（类型为 l），大小 = 8 字节（"test.txt" 的字符长度）
  • 如果你删了 test.txt 再访问 soft.txt：软链接会"断链"（dangling symlink），而 link.txt 通过 inode 还在，数据安然无恙
📝 练习 2：查看 dcache 的统计信息
# 查看 slab 中 dcache 和 inode 缓存的使用情况
grep -E "(dentry|inode)" /proc/slabinfo | head -5

# 查看 VFS 层面的统计信息
cat /proc/sys/fs/dentry-state
cat /proc/sys/fs/inode-state
🔍 展开说明

这些文件显示了当前系统上 dcache 和 inode 缓存的状态。你之前学过的 slab 分配器（09-物理内存管理/下）正是用来管理 dentry 和 inode 对象缓存的内核机制。

dentry-state 第一列是当前 dentry 总数，第二列是正在使用的 dentry 数，第三列是"无用但暂未回收"的 dentry 数（这部分可以被内存回收机制收回）。

7. 知识测验

回答以下问题，点击选项后查看反馈：

1️⃣ 下面哪个 VFS 对象 只存在于内存中，从不会被写入磁盘？
正确答案：C. dentry
dentry 是纯内存结构，只在 dcache 中用于加速路径解析。而 file 虽然也是内存中的对象，但它不代表"路径名到 inode 的映射"——它表示的是进程的打开上下文。题目问的是"从不会被写入磁盘"，file 确实不写磁盘，但 dentry 的概念更核心地体现了"内存缓存"的设计思想。注意区分：dentry 缓存的是目录结构关系，file 是打开状态。
2️⃣ 两个进程分别打开同一个文件，它们共享哪些 VFS 对象？
正确答案：C
每个 open() 调用都会创建一个新的 file 对象（独立的 f_pos、f_mode），但 dentry 和 inode 是全局共享的。这也解释了为什么两个进程同时读写同一文件时，各自的读写位置不会互相影响（除非故意用 O_APPEND 或文件锁）。
3️⃣ 执行 rm test.txt 后，什么情况下 inode 和数据才会被真正释放？
正确答案：C
rm 相当于 unlink()，让 i_nlink 减 1。只有当 i_nlink == 0（没有 dentry 指向它）且 i_count == 0（没有 file 对象引用它）时，内核才会调用 iput_final() 释放 inode 和对应的数据块。这就是"文件已删除但空间没释放"的经典原因。
