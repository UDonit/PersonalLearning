从 open() 到 read()

第二课我们跟完了 open() 的九步旅程——拿到了 fd，建立了完整的引用链。但 open 只是敲门，真正干活的是 read()。

read(fd, buf, 4096)——用户的 4096 字节数据，从哪里来？
答案：从 Page Cache（页缓存）来。如果缓存有，直接复制到用户空间；如果缓存没有，才从磁盘读。

Page Cache 是 Linux 文件系统性能的绝对基石。可以这么讲：没有 page cache，文件系统性能会慢 1000 倍以上。

1. Page Cache 是什么？

📦 定义

Page Cache 是内核用物理内存页面来缓存磁盘文件数据的机制。每个缓存页的大小等于系统页面大小（通常是 4KB）。

当你 read() 一个文件时：

  • 如果数据已经在 page cache 中 → 直接从内存复制到用户缓冲区（纳秒级）
  • 如果数据不在 page cache 中 → 从磁盘读到 page cache，再复制到用户缓冲区（毫秒级）

1.1 核心数据结构：address_space

每个 inode 都有一个 i_mapping 指针，指向它的 struct address_space——这是连接 inode 和 page cache 的桥梁。

// include/linux/fs.h
struct inode {
    // ...
    struct address_space    *i_mapping;     // ← page cache 的入口
    struct address_space    i_data;          // ← 内嵌的 address_space（大部分文件用这个）
    // ...
};

struct address_space {
    struct inode            *host;           // 指向所属的 inode（反向关联）
    struct xarray           i_pages;        // ★ 存储所有缓存页的数据结构（xarray）
    struct address_space_operations *a_ops;  // 操作函数表
    struct rb_root_cached   i_mmap;         // 共享映射（mmap 用）
    atomic_t                i_mmap_writable; // 可写共享映射计数
    unsigned long           nrpages;        // 当前缓存的页面数量
    // ...
};
```

1.2 xarray：page cache 的索引结构



以前叫 radix tree，在较新内核中改为 xarray（本质上还是基树，但 API 更简洁）。它解决的问题是：给定文件偏移量（0, 4096, 8192...），快速找到对应的缓存页。



一个 16 KB 文件（4 页）的 xarray：










// xarray 查找的核心操作
// 给定文件偏移 → 找到对应的 page cache 页
struct page *pagecache_get_page(struct address_space *mapping,
                                pgoff_t index,    // 页索引 = offset >> PAGE_SHIFT
                                int fgp_flags,    // 查找标志
                                gfp_t gfp_mask)
{
    // 在 xarray 中查找
    page = xa_load(&mapping->i_pages, index);
    if (page)
        return page;

    // 如果找不到且要求分配 → 新建页并插入 xarray
    page = __page_cache_alloc(gfp_mask);
    xa_store(&mapping->i_pages, index, page, gfp_mask);
    return page;
}




性能关键：xa_load() 是 O(1) 的——基数树的高度固定（对于 4KB 页、64 位系统，树高 ≈ 6 层就覆盖了整个文件系统的 64 位地址空间）。



2. read() 的完整旅程（七步）



假设我们已经 open() 拿到了 fd=3，现在调用 read(3, buf, 4096)：







  第 1 步：libc 封装 → syscall
  
与 open 类似，libc 的 read() 包装函数将 fd、buf、count 存入寄存器（rdi=3, rsi=buf, rdx=4096），执行 syscall，切换到内核态。

  
glibc/sysdeps/unix/sysv/linux/read.c






  第 2 步：syscall 入口 → vfs_read()
  
系统调用号 0（__NR_read），从 sys_call_table 找到 ksys_read()。它根据 fd=3 从进程的 fdtable 中找到对应的 struct file，然后调用 VFS 层的统一入口 vfs_read()。

  
fs/read_write.c — ksys_read() → vfs_read()






  第 3 步：VFS 层分发 → file->f_op->read_iter()
  
vfs_read() 做两件事：

  
    
    
  • 检查权限（file 的 f_mode 是否可读）
    • 
    
  • 调用 file->f_op->read_iter()
    • 
  

  
对于 ext4 普通文件，这个函数指针是 ext4_file_read_iter()。但对于 procfs 里的文件，这里的函数就完全不同了。

  
fs/read_write.c — vfs_read()






  第 4 步：通用文件读取 → generic_file_read_iter()
  
ext4 的 read_iter 调用 通用文件读取函数 generic_file_read_iter()。这是 page cache 的核心入口。

  
mm/filemap.c — generic_file_read_iter()






  第 5 步：filemap_read() — page cache 查找 (最核心)
  
这是决定性的一步。filemap_read() 的核心逻辑：


  
// mm/filemap.c — filemap_read() 核心循环（极度简化）
ssize_t filemap_read(struct kiocb *iocb, struct iov_iter *iter,
                     ssize_t already_read)
{
    struct address_space *mapping = file->f_mapping;
    pgoff_t index = iocb->ki_pos >> PAGE_SHIFT;  // offset → 页索引

    do {
        // ① 在 page cache 中找这一页
        folio = filemap_get_folio(mapping, index);

        if (IS_ERR(folio)) {
            // ② 没命中！从磁盘读
            //    ★ filemap_readahead() — 发起预读（一次可能读多页）
            //    ★ mapping->a_ops->read_folio() — 读一页
            //    → 磁盘 I/O → 磁盘数据到内存页
            //    → 页现在在 page cache 中了
        }

        // ③ 把页中的数据复制到用户缓冲区
        //    copy_page_to_iter() — 真正的数据传递
        //    ↑ 这就是"read"最终做的事情

        index++;  // 下一页
    } while (还有数据要读);

    return total_read;  // 返回实际读取的字节数
}
  


  
mm/filemap.c — filemap_read()






  第 6 步：未命中时的磁盘 I/O 路径
  
page cache 没命中的情况下，内核需要从磁盘读取数据。以 ext4 为例：


  
// 预读（page_cache_sync_readahead()）判断需要读哪些页
// → mapping->a_ops->read_folio()
//   → ext4_read_folio()              (fs/ext4/inode.c)
//     → __block_read_full_folio()    (fs/buffer.c)
//       → 创建 bio（块 I/O 请求）
//       → submit_bio()                (block/blk-core.c)
//         → 通用块层
//           → I/O 调度器（mq-deadline / BFQ）
//             → 磁盘驱动程序
//               → DMA 传输到 page cache 页
//                 → 完成！数据在 page cache 中了
//                   → 回到第 5 步的 copy_page_to_iter()
  


  
fs/ext4/inode.c → fs/buffer.c → block/blk-core.c → 块层...






  第 7 步：数据复制到用户态 → 返回
  
copy_page_to_iter() 将 page cache 页中的数据拷贝到用户空间的缓冲区 buf。如果命中缓存，这是整个 read() 中唯一的内存操作，没有磁盘 I/O。然后 ki_pos += count，返回实际读取的字节数。

  
lib/iov_iter.c — copy_page_to_iter()

3. 预读（Readahead）——让大部分 read() 命中的关键



如果每次 read() 都等缺页才触发 I/O，性能还是不够。因为 read() 通常是顺序访问的。



内核的读优化策略：预读（readahead）——当你读第 0 页时，内核推测你会读第 1、2、3 页，提前把它们也从磁盘读到 page cache 中。



// mm/readahead.c — 预读逻辑的核心决策
void page_cache_sync_readahead(struct address_space *mapping,
                               struct file_ra_state *ra,
                               struct file *file,
                               pgoff_t index)
{
    // 判断是否为顺序访问
    if (index == ra->start + ra->size) {
        // ★ 顺序访问 → 增大预读窗口
        //    典型的预读大小递增：
        //    第 1 次 → 4 页（16KB）
        //    第 2 次 → 8 页（32KB）
        //    第 3 次 → 16 页（64KB）
        //    ……直到上限（通常 128KB~2MB）
        ra->size = min(ra->size * 2, ra->ra_pages);
    } else {
        // 随机访问 → 保守，只读需要的页
        ra->size = 0;
    }

    // 发起预读 I/O
    read_pages(mapping, file, &page_list, ra->size);
}












  💡 预读的赌注：内核赌你对文件是顺序读的。事实是绝大多数场景确实是顺序读（cat、日志处理、数据拷贝、流媒体播放）。赌对了性能大赚；赌错了（随机访问）浪费一次 I/O 带宽但不会出错——读到 page cache 的页最多被 LRU 回收掉。




4. 脏页与回写（Writeback）



write() 的路径和 read() 对称——数据先写入 page cache，标记页为"脏"（dirty），然后内核异步写回磁盘。



// write() 的核心简化流程
write(fd, buf, 4096)
  → vfs_write()
    → file->f_op->write_iter()
      → generic_perform_write()
        → iov_iter_copy_from_user_atomic()  // 从用户空间拷贝到 page cache
        → mark_buffer_dirty()               // 标记为脏页
        → 返回（数据还在内存，还没到磁盘！）

// 脏页回写（内核异步，由 flusher 线程执行）
// 触发条件：
//   1. 脏页比例超过 /proc/sys/vm/dirty_background_ratio（默认 10%）
//   2. 脏页存在时间超过 /proc/sys/vm/dirty_expire_centisecs（默认 30 秒）
//   3. 调用 fsync() / sync() 同步强制回写

5. 知识测验




  
1️⃣ 执行 read(fd, buf, 4096) 时，以下哪个操作一定发生？

  
  
  
  
  

    正确答案：C

    read() 无论如何都要把数据从 page cache 复制到用户缓冲区。如果缓存命中，A 和 D 都不会发生；B 只在缓存未命中且需要新页时发生。只有 C 是 read() 的必经之路。
  






  
2️⃣ 预读（readahead）在什么情况下会"自动紧缩"？

  
  
  
  
  

    正确答案：C

    预读的"赌注"是顺序访问。如果内核发现 read() 请求的页不在预读窗口内（比如 ra->start + ra->size 不等于当前 index），就判定为随机访问，将预读大小降为 0，不再浪费 I/O。
  






  
3️⃣ write() 调用返回后，数据一定在磁盘上了吗？

  
  
  
  
  

    正确答案：A

    write() 的默认行为是"写回缓存（write-back）"——数据写入 page cache 就返回，标记为脏页。内核后台线程（flusher）异步回写。如果需要确保数据在磁盘上，必须调用 fsync()。这也解释了为什么机器突然断电会丢数据——page cache 中的脏页还没写回磁盘。选项 C "一定不在" 过于绝对。
  






  
4️⃣ 两个进程分别打开同一个文件并执行 read()，它们各自读到的数据来自于同一个物理内存页吗？

  
  
  
  
  

    正确答案：A

    page cache 是全局共享的。两个进程的 struct file 不同，但它们指向同一个 inode → 同一个 address_space → 同一个 page cache。read() 时各自调用 copy_page_to_iter() 把同一页的数据复制到各自的用户缓冲区。这也意味着：进程 A 先读触发磁盘 I/O 将数据读入 page cache，进程 B 后读直接从 page cache 命中——零 I/O。
