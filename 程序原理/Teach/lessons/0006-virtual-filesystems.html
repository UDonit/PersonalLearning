🧠 第六课：虚拟文件系统——没有磁盘的文件系统怎么工作？

主题：procfs、sysfs、tmpfs——以内存/数据结构为"存储介质"的文件系统
前置知识：第一课（VFS 四对象）、第二课（dcache 与 lookup）、第三课（page cache）
预估时间：35–45 分钟

前五课的前提——"有磁盘"

前五课我们从 VFS 一直走到 ext4 的磁盘布局和 Journal，所有内容都建立在一个前提上：文件系统的数据最终存放在磁盘上。

但 Linux 里有一类文件系统根本没有磁盘：

$ ls -la /proc/self/status
-r--r--r-- 1 root root 0 Jun 25 10:00 /proc/self/status

$ cat /proc/self/status
Name:   cat
State:  R (running)
Pid:    1234
VmRSS:       1234 kB
...

$ stat -f /proc
File: "/proc"
    ID: 0        Namelen: 255     Type: proc
Block size: 4096    Fundamental block size: 4096
Blocks: Total: 0      Free: 0      Available: 0

🔍 注意看：Blocks: Total: 0——procfs 没有数据块的概念。它的大小在 stat 里总是 0，因为文件内容是"读的时候现生成的"。

💡 核心问题：没有磁盘，那它的 inode 从哪来？它的数据存在哪？lookup() 怎么做？page cache 还有意义吗？

答案是：全部在内存中动态生成。虚拟文件系统是 VFS 虚函数表设计哲学的极致体现。

1. VFS 的"依赖倒置"——回顾第一课的核心洞见

第一课我们学到：VFS 定义了四个核心对象，每个对象都包含一个操作函数表，不同的文件系统各自实现这些函数：

VFS 对象              操作函数表
─────────────────────────────────────
超级块 → super_operations  → alloc_inode, destroy_inode, write_inode, ...
inode   → inode_operations → lookup, create, mkdir, link, ...
文件    → file_operations  → read_iter, write_iter, open, fsync, mmap, ...
dentry  → dentry_operations → d_revalidate, d_delete, ...

这正是依赖倒置原则的体现：VFS 不依赖具体文件系统的实现，具体文件系统实现 VFS 定义的接口。ext4 调用 ext4 的磁盘 I/O 例程；procfs 调用内核数据结构的读取例程——对 VFS 来说，它们长一个样。

2. procfs——/proc 就是进程数据结构的"文件系统视图"

2.1 核心哲学

procfs 不是一个"存储文件内容的文件系统"，它是一个内核数据结构的动态展示窗口。每次你读 /proc 下的文件，内核都在"现编"文件内容。

$ cat /proc/self/status  # 你每次读，内容都可能不同
Name:   cat               # 当前运行的进程名
Pid:    1234              # 进程 ID
VmRSS:  1234 kB           # 实时 RSS → 内存管理子系统当前的数据

# 对比：ext4 文件读出来每次都一样（除非被修改）
$ cat /home/user/doc.txt  # 存什么读什么

2.2 procfs 的目录树就是进程树

/proc ├── 1/ ← 进程 #1 (init/systemd) 的目录 │ ├── cmdline ← 进程启动命令行 │ ├── cwd → / ← 进程当前工作目录（软链接） │ ├── fd/ │ │ ├── 0 → /dev/pts/0 ← 标准输入 │ │ ├── 1 → /dev/pts/0 ← 标准输出 │ │ └── 2 → /dev/pts/0 ← 标准错误 │ ├── maps ← 进程内存映射（mmap 区域） │ ├── status ← 进程状态（Name, State, Pid, VmRSS, ...） │ ├── stack ← 内核栈回溯 │ └── root/ ← 进程的根文件系统（chroot 后此目录可见） ├── self/ ← 指向当前进程的软链接（/proc/self → /proc/1234） ├── cpuinfo ← CPU 信息（从 per-CPU 数据生成） ├── meminfo ← 内存使用情况（从内存管理子系统生成） ├── version ← 内核版本号 └── uptime ← 系统运行时间

2.3 procfs 的文件生成过程——以 /proc/self/status 为例

用户调用 read()

read(fd, buf, 4096) → vfs_read() → file->f_op->read_iter()

procfs 的 read_iter

proc_reg_read_iter() → 查找这个文件对应的 proc_ops（proc 操作表）

调用 proc 文件对应的 proc_ops->proc_read()

每个 proc 文件注册了自己的"生成函数"。例如 status 文件的生成函数是 proc_pid_status()：

proc_pid_status() 中发生了什么 
// fs/proc/array.c — 简化的伪代码
int proc_pid_status(struct seq_file *m, struct pid_namespace *ns,
                    struct pid *pid, struct task_struct *task)
{
    // 从 task_struct 中读取字段，逐行格式化到 seq_file
    task_name(m, task);        // → "Name:\tcat\n"
    task_state(m, task);       // → "State:\tR (running)\n"
    task_pid(m, task);         // → "Pid:\t1234\n"
    task_sig(m, task);         // → 信号相关信息
    task_mem(m, task);         // → "VmRSS:\t1234 kB\n"  ← 读 mm_struct
    // ...
    return 0;
}
数据组装到 seq_file 缓冲区

seq_file 是内核的"顺序文件"辅助机制——procfs 将格式化文本写入 seq_file 的内核缓冲区，然后 copy_to_user() 到用户空间。整个过程不涉及 page cache（除了 seq_file 自己的内核缓冲区）。

💡 关键差异：ext4 的 read() 从磁盘读数据到 page cache，再从 page cache 拷贝到用户空间。procfs 的 read() 从task_struct、mm_struct 等内核数据结构中格式化出文本，直接拷贝到用户空间。procfs 不经过 page cache——因为内容每次读都可能不同，缓存没有意义。

2.4 seq_file——procfs 的"打印机"

seq_file 是内核专门为"顺序文件"（如 procfs、sysfs 中那些读一次就生成全部内容的文件）设计的辅助 API：

// seq_file 的工作方式：
//
// 用户 read() → seq_file 调用 show() 回调 → show() 用 seq_printf() 输出文本
//
// 内核开发者只需要实现一个 show() 函数：
static int my_proc_show(struct seq_file *m, void *v)
{
    struct task_struct *task = current;
    seq_printf(m, "Name:\t%s\n", task->comm);   // ← 格式化输出
    seq_printf(m, "Pid:\t%d\n", task->pid);
    return 0;
}
// seq_file 帮你处理了缓冲区管理、分页、seek 等所有细节

2.5 procfs 的 inode 从哪来？

procfs 挂在 VFS 上，所以它必须有 inode。这些 inode 是在内存中动态创建的：

// 伪代码：procfs 挂载时创建根 inode
struct inode *proc_root_inode = new_inode(proc_sb);  // 分配内存中的 inode
proc_root_inode->i_mode = S_IFDIR | 0555;
proc_root_inode->i_ino = PROC_ROOT_INO;  // inode #1（proc 命名空间内部）
proc_root_inode->i_op = &proc_root_inode_operations;
proc_root_inode->i_fop = &proc_root_file_operations;
// → 不涉及任何磁盘 I/O

// lookup() 时：创建新的子 inode
struct dentry *proc_lookup(struct inode *dir, struct dentry *dentry)
{
    // 查找进程 PID 目录 → 如果进程存在，创建 inode
    struct task_struct *task = find_task_by_pid(pid);
    if (!task)
        return ERR_PTR(-ENOENT);         // 进程不存在 → ENOENT

    inode = proc_pid_make_inode(dir->i_sb, task);  // 分配 inode，填充
    inode->i_fop = &proc_tgid_base_operations;
    d_add(dentry, inode);                          // dentry 指向 inode
    return NULL;                                   // 成功
}

这些 inode 只存在于内存中——kmalloc 分配、用完 kfree 释放，不存在"写回磁盘"的概念。

3. sysfs——设备模型的文件系统视图

3.1 从 kobject 到文件路径

sysfs 基于内核的设备模型（driver model），核心概念是 kobject（kernel object）。每个 kobject 在 sysfs 中对应一个目录，kobject 的属性（attribute）对应目录下的文件：

/sys/
├── devices/              ← 所有设备
│   ├── pci0000:00/
│   │   ├── 0000:00:02.0/ ← 一个 PCI 设备
│   │   │   ├── vendor    ← 读这个文件 → 返回 "0x8086"（Intel）
│   │   │   ├── device    ← 返回设备 ID
│   │   │   └── driver → ../../../../bus/pci/drivers/i915/
│   │   └── ...
│   └── ...
├── bus/                  ← 所有总线类型
│   ├── pci/
│   ├── usb/
│   └── ...
├── class/                ← 设备分类（按功能）
│   ├── net/              ← 网络设备
│   │   └── eth0/
│   ├── input/            ← 输入设备
│   └── ...
├── block/                ← 块设备
│   ├── sda/
│   └── ...
└── kernel/               ← 内核参数
    ├── mm/
    ├── uevent_helper
    └── ...

3.2 设备驱动注册与 sysfs 文件自动生成

// 驱动注册 → 自动创建 sysfs 目录和文件
// 以 PCI 设备为例：

pci_register_driver(&my_driver);
  → driver_register()
    → kobject_add()           ← 在 /sys/bus/pci/drivers/my_driver/ 建目录
    → 如果发现设备:
      → device_add()
        → kobject_add()       ← 在 /sys/devices/pci0000:00/0000:00:xx.x/ 建目录
        → device_create_file() ← 在设备目录下创建属性文件

// 属性文件 = 一组 show()/store() 回调
static struct device_attribute dev_attr_my_value = {
    .attr = { .name = "my_value", .mode = 0644 },
    .show = my_value_show,   // 读文件时调用
    .store = my_value_store, // 写文件时调用
};

// cat /sys/devices/.../my_value → 内核调用 my_value_show()
static ssize_t my_value_show(struct device *dev,
                             struct device_attribute *attr,
                             char *buf)
{
    struct my_dev *my = dev_get_drvdata(dev);
    return sprintf(buf, "%d\n", my->value);  // 从驱动数据结构读取
}

// echo 42 > /sys/devices/.../my_value → 内核调用 my_value_store()
static ssize_t my_value_store(struct device *dev,
                              struct device_attribute *attr,
                              const char *buf, size_t count)
{
    struct my_dev *my = dev_get_drvdata(dev);
    my->value = simple_strtol(buf, NULL, 10);  // 写入驱动数据结构
    return count;
}

3.3 从 /sys/class/net/eth0/statistics/tx_bytes 看链路

这个路径追踪了发送字节数——网络驱动实时更新：

/sys/class/net/eth0/statistics/tx_bytes  →  read()
  → sysfs_kf_read()
    → dev_attr_show() → ethtool 回调
      → 从 net_device->stats.tx_bytes 读取
      → 返回 "12345678\n"

每次读都是实时值，因为这个值在内核中由网络驱动持续更新。sysfs 文件没有 page cache——读就是读，直接穿透到内核数据。

4. tmpfs——基于内存的"文件系统"

tmpfs 是一个特殊的存在——它有 page cache，有 inode，有 dentry，但没有磁盘。它的"存储"是 swap 空间（虚拟内存）。

4.2 磁盘文件系统 vs tmpfs vs procfs —— 数据流对比

ext4

数据在磁盘上。

read() → 磁盘 → page cache → 用户
write() → 用户 → page cache → 磁盘

tmpfs

数据在page cache中。

read() → page cache → 用户
write() → 用户 → page cache
(有内存压力时 → swap)

procfs

数据在内核数据结构中。

read() → task_struct → 格式化 → 用户
没有 page cache，没有磁盘，
内容是"现编"的

4.3 tmpfs 的"千万要记住"——写 tmpfs 不等于写内存安全

⚠️ 常见误区：很多人以为 "tmpfs 在内存中，重启就没了，但运行时是安全的"。

问题是：如果系统内存不足（OOM），tmpfs 的数据可能被换出到 swap——而 swap 分区在重启后是垃圾数据。所以 tmpfs 既不持久也不安全——它只是"一般情况下在内存中"。

另外，tmpfs 上的文件可以通过 fsync() 刷脏页到 swap，但这种"持久化"在重启后无效。

6. 思考题

1️⃣ procfs 的文件内容在什么时候生成？
正确答案：C
procfs 的文件内容不是在创建或挂载时固定的。每次 read() 时，内核调用对应的 proc_ops->proc_read() 回调，从内核数据结构中实时读取/格式化数据。这就是为什么两次读 /proc/meminfo 可能得到不同结果。
2️⃣ procfs 为什么不使用 page cache？
正确答案：C
procfs 读取的是实时内核数据（进程状态、内存使用、CPU 信息等），这些数据随时在变化。如果使用 page cache，读到的可能是"过期"的数据——违背了 procfs"实时展示"的设计目标。seq_file 机制提供的"按需生成+直接输出"模式更合适。
3️⃣ tmpfs 的数据在系统重启后还在吗？
正确答案：A
tmpfs 的数据在 page cache 中，底层没有持久存储。即使被换出到 swap（内存压力时），swap 分区在重启后是垃圾数据。所以 tmpfs 是"临时"的——系统运行期间可用，重启后一切消失。这也是为什么它叫 tmpfs（temporary filesystem）。
4️⃣ 你有一个 ext4 文件和一个 procfs 文件，分别 open 后在两个文件上同时 read()。VFS 如何区分它们？
正确答案：C
VFS 不关心"什么类型的文件系统"。每个 file 对象都持有自己的 f_op 指针——ext4 文件的 f_op 指向 ext4_file_operations（含 ext4_file_read_iter），procfs 文件的 f_op 指向 proc_reg_file_operations（含 proc_reg_read_iter）。VFS 调用 file->f_op->read_iter() 时，自然走到了各自不同的实现。
5️⃣ sysfs 中 "cat /sys/class/net/eth0/statistics/tx_bytes" 读到的是什么时候的数据？
正确答案：A
sysfs 属性文件的 show() 回调直接从设备驱动数据结构中读取实时值。对于网络统计，驱动会在每次数据包发送/接收时更新 net_device->stats 中的计数器。cat 该文件时，show() 回调只做一个 sprintf() 将当前计数器的值格式化成字符串返回——所以永远是最新的。
