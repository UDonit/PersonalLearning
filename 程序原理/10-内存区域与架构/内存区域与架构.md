# 10 内存区域与架构 - 问题驱动的学习指南

> 本指南用于引导学习 SMP、NUMA 架构，以及 Linux 内核中 ZONE 区域划分的原理。
> 建议按问题逐节探索，每节完成后将笔记整理为 "我当前的理解 / 我验证过的现象 / 我仍然没想透的问题" 三部分。

## 前言：本章在主线中的位置

在 09 章我们了解了伙伴系统如何管理物理内存，但有一个前提被刻意忽略了：伙伴系统对物理内存的"平面"视角。

实际上，在真实硬件中，不同的 CPU 访问不同位置的物理内存，延迟可能是完全不同的。此外，某些硬件（如老式 ISA 设备）只能访问物理内存的低 16MB。这就引出了本章的核心：

- **SMP（对称多处理）**：多个 CPU 共享同一总线、同一内存控制器，访问所有内存延迟相同
- **NUMA（非一致内存访问）**：每个 CPU（或 CPU 组）有自己"近端"的内存，访问远端内存延迟更高
- **ZONE（内存区域）**：内核将物理内存按"用途约束"划分为不同区域，解决硬件寻址能力差异，并在 NUMA 下与节点交织

**建议回顾**：

- 09 章中 `struct memblock_region` 里 `#ifdef CONFIG_NUMA` 的 `int nid` 成员
- 09 章中 `struct page` 数组如何与物理内存一一对应
- 08 章中 MMU、页表、物理页之间的关系

## 一、SMP 架构

### 1.1 SMP 是什么？

**核心概念**：SMP 系统中所有 CPU 地位平等，共享同一物理地址空间和内存总线，任何 CPU 访问任意内存位置的延迟理论上一致。

**学习目标**：

- 画出 SMP 的硬件拓扑示意图（CPU ←→ 共享总线 ←→ 内存控制器 ←→ 内存）
- 理解"对称"的含义：所有 CPU 运行同一操作系统、访问同一内存
- 对比单处理器系统的差异

**可能必须理解的关键问题**：

- 既然所有 CPU 共享一根总线，多个 CPU 同时访问内存是否会产生竞争？
  - 会产生竞争，会出现总线仲裁（bus arbitration）的情况，会导致其他CPU要等待当前CPU访问结束后才可以继续尝试访问，等待期间 CPU 不能做别的事情，会显著增加内存访问延迟，是这种拓扑架构的性能瓶颈

- 缓存一致性（cache coherency）在 SMP 中是如何保证的（MESI 协议等）？
  - 是通过MESI协议来保证，MESI协议是各个CPU之间存在缓存交互
  - 每个 CPU 的缓存控制器持续监听（snoop）共享总线上的所有内存事务
  - 当某个 CPU 要读/写某地址时，会广播自己的请求到总线上
  - 其他 CPU 的缓存控制器听到后，检查自己是否缓存了该地址（cache line），并做出响应
  - 协议通过 4 种状态转换来保证一致性：
    - M：modified，本CPU独占，数据已被修改，与内存不一致
    - E：exclusive，本CPU独占，但数据与内存一致
    - S：shared，多CPU都有，缓存干净
    - I：invalid，缓存失效
  - 当一个 CPU 想写入一个 S 状态的行时，必须先广播 `Bus Upgrade`（或 `BusRdX`）请求，其他 CPU 收到后把自己的副本置为 I
  - 然后写者获得独占权（M 状态）
- SMP 系统的可扩展性瓶颈在哪里？（提示：总线带宽）
  - 所有对内存的访问都需要经过内存访问控制器或者北桥，这里会成为性能瓶颈
  - 缓存一致性流量也会导致性能下降
  - 因此NUMA 把总线竞争限制在节点内部，跨节点走互联总线，本质上是绕开 SMP 的扩展性瓶颈。


**建议验证**：

- 在自己的开发环境中执行 `lscpu` 或 `cat /proc/cpuinfo`，观察 CPU 数量和拓扑
- 思考：为什么现代多核笔记本大多仍是 SMP，而非 NUMA？

### 1.2 Linux 内核针对 SMP 做了哪些适配？

**学习目标**：

| 机制 | 解决的问题 | 核心思想 |
|------|-----------|---------|
| **自旋锁（spinlock）** | 多个 CPU 同时访问临界区 | 忙等的轻量锁，持有者短时间内释放 |
| **每 CPU 变量（percpu）** | 减少 CPU 间的缓存行竞争 | 每个 CPU 持有自己的变量副本 |
| **RCU（Read-Copy-Update）** | 读多写少场景下的无锁同步 | 写者复制修改，读者无锁访问旧数据 |
| **中断亲和性（IRQ affinity）** | 中断处理分散到多 CPU | 将特定中断绑定到特定 CPU |

**可能必须理解的关键问题**：

- per-CPU 变量为什么能减少缓存行乒乓（cache line bouncing）？
  - cache line bouncing主要发生在多个CPU对同一个变量的更新，1个CPU更新值后，会导致其他CPU对应的缓存失效需要重新拉取
  - per-CPU则每个变量都保存在CPU自己的缓存中，不会出现缓存失效的问题
  - 内核可以使用DEFINE_PER_CPU
  - 数据之间避免伪共享（同一个cache line）

- 自旋锁 vs 互斥锁（mutex）：什么场景该用什么？
  - 自旋锁获取失败时不会导致内核线程进入休眠重新调度其他线程，而互斥锁如果失败，内核线程会先进入睡眠模式，内核会调度其他线程先运行，后续唤醒后存在上下文切换的消耗
  - 在知道锁会很快获取到的情况下，使用自旋锁效果更好。而不确定锁多久能获取到，可以用互斥锁。
  - 在不可睡眠的上下文中，不能使用互斥锁

- 内核中哪些数据结构使用了 per-CPU 优化？（提示：伙伴系统的 `free_area` 之外还有 per-CPU 页缓存）
  - 内核中的通用分配器回收的缓存页并未立即返还给伙伴系统，使用了per-CPU变量来缓存
  - 内核中大部分的计数都是per-CPU
  - 一些中断处理中的变量也是per-CPU


**建议验证**：

- 搜索内核源码中 `DEFINE_PER_CPU` 和 `get_cpu_var` 的使用
- 阅读 `/proc/interrupts`，观察中断在各 CPU 上的分布

## 二、NUMA 架构

### 2.1 NUMA 是什么？

**核心概念**：NUMA 系统中 CPU 和内存被划分为多个"节点（Node）"，每个节点有自己的本地内存。CPU 访问本地内存速度快，访问其他节点的远端内存速度慢。

**学习目标**：

- 画出 NUMA 的硬件拓扑示意图（Node0: CPU + 本地内存 ⟷ 互联总线 ⟷ Node1: CPU + 本地内存）
- 理解 NUMA 节点的概念以及 UMA（Uniform Memory Access，一致内存访问）与 NUMA 的本质区别
- 理解 NUMA 的诞生背景：SMP 的多 CPU 总线争抢瓶颈

**可能必须理解的关键问题**：

- NUMA 的"距离"（distance）是什么？内核如何量化？（提示：SLIT 表）
  - NUMA的距离指的是访问RAM的相对成本。
  - 同一个节点内访问的距离为10（基准单位），其他节点的值都是 10 的倍数（例如 20 表示"两倍于本地访问的开销"）
  - SLIT表是ACPI 标准定义的表，由 BIOS/UEFI 固件在系统启动时提供
  - 用矩阵来记录这个相对成本，行是源节点，列是目标节点
  - 内核启动时会解析这种表，并且调度和页分配都基于这张表做决策
  - **SRAT（System Resource Affinity Table）**，告诉内核每个内存段属于哪个 NUMA 节点
    - 对上memblock分配器机制，memblock通过E820获取所有物理内存段后，需要通过`acpi_numa_init()`解析归属节点，然后填写nid(E820 在现代 BIOS 中已经支持携带 proximity domain 信息（通过 Extended Attributes 的 Type 7，Type 7 也叫 Address Range Extended Attributes）。所以 E820 自身就能携带节点号，SRAT 在很多情况下是做"复核"和"补充"。)
    - 后续伙伴系统交接的`pg_data_t`也是基于nid来划分资源

- 什么是"Node Interleaving"（节点交织）？为什么要关闭或开启？
  - Node Interleaving是指内核为应用程序等分配内存不再按NUMA节点来分配，而是改为有规律的交替分配不同NUMA下的内存给应用
  - 秉承的思想是：如果应用没办法做到最优，那么也不要让性能变成最差，这样交替分配后应用程序访问内存的代价就变成了访问各个NUMA的平均消耗
  - 默认是关闭的，可以选择开启，毕竟开启后是对全局造成影响
  - 支持进程级别的交织策略 — `mbind()` / `set_mempolicy(MPOL_INTERLEAVE)`，让特定进程使用交织分配而不影响全局

- NUMA 的"本地访问"和"远端访问"性能差异有多大？什么情况下远端访问会成为瓶颈？
  - 本地访问性能是最高的，是0Hop，远端访问可能要经过1Hop或者2Hop等，性能差异可能在2到3倍。
  - 任何情况下，远端访问都是影响性能的问题之一，但成为瓶颈一般针对大量跨节点访问导致整体吞吐下降的情况


**建议验证**：

- 执行 `numactl --hardware` 查看当前系统的 NUMA 拓扑（如果有 NUMA 的话）
- 执行 `numastat` 查看各节点的内存分配与远端访问统计
- 如果是单 NUMA 节点的机器，使用 `dmesg | grep -i numa` 查看内核的 NUMA 初始化日志
- 思考：为什么云服务器通常是单 NUMA 节点，而物理服务器通常是双节点？

### 2.2 Linux 内核针对 NUMA 做了哪些适配？

**学习目标**：

理解内核的 NUMA 感知策略：

| 策略 | 行为 | 适用场景 |
|------|------|---------|
| **节点本地分配** | 优先从当前 CPU 所在节点分配内存 | 通用默认策略 |
| **内存迁移** | 将进程的内存迁移到其运行的 CPU 所在节点 | 进程迁移后优化 |
| **NUMA 平衡（sched_numa_balancing）** | 调度器主动检测并优化进程的内存放置 | 自动 NUMA 优化 |
| **交错分配（interleave）** | 将内存均匀分布到所有节点 | 避免单节点内存压力 |

**可能必须理解的关键问题**：`

- 内核在 `alloc_pages()` 时如何确定从哪个 NUMA 节点分配？
  - alloc_pages其实是封装了`alloc_pages_node()`函数，使用`numa_node_id()`确定nid，如果此时给的参数是`NUMA_NO_NODE`，在`alloc_pages_node()`中还会基于NUMA亲和性选择一个恰当的nid。然后分配对应的本地内存
  - 通过numa_node_id()确定首选节点
  - 如果有内存策略（mempolicy），则根据策略选择zone，不然就基于GPF对应的zonelist里的顺序与申请的标志位，选择一个zone
  - 如果目标zone没有足够的内存，则基于fallback机制往后尝试其他zone
  - zone的优先级基本是按照`ZONE_MOVABLE → ZONE_NORMAL → ZONE_DMA32 → ZONE_DMA`
  - 要注意是基于GFP标志位来看zonelist的，例如`GFP_KERNEL`给内核分配的物理页，就没有`ZONE_MOVEABLE`，因为不允许迁移

- `mempolicy`（内存策略）系统调用（`set_mempolicy`, `mbind`）允许用户态做什么？
  - 允许用户态设置从哪个 NUMA 节点分配内存，以及按什么策略分配（如 BIND 绑定节点、INTERLEAVE 节点间轮转）
- NUMA 平衡（Automatic NUMA Balancing）的触发条件和工作原理是什么？
  - NUMA平衡的触发条件有两个：
    - 1. 负载均衡，当一个NUMA节点分配过多而其他NUMA节点分配较少时，会触发NUMA平衡对进程和内存的迁移
      2. 性能监控，当内核发现一个进程总是在跨节点访问内存时，他可能会将访问的内存迁移到进程所在节点，也可能把进程迁移到内存所在节点，取决于两者的迁移难度，依据的是成本估算：`task_numa_fault()` 中对迁移成本的比较
    - 工作原理是基于物理页的访问做检查，通过NUMA监控线程（ task_numa_work() 周期性执行（默认约 5ms））定期清除PTE的访问位，从而触发进程的缺页异常，然后对比进程所在的CPU的numa_node_id()是否与物理页的nid相同，不同的话则得知是跨节点访问，会增加计数。当计数累计到一定次数后会触发平衡逻辑。
      - 为什么不会与kswapd的回收逻辑冲突：因为在缺页异常中有区分，`pte_protnone(vmf->orig_pte) && vma_is_accessible(vmf->vma)`，这个才是task_numa_work()设置的缺页。
      - task_numa_work清除的是Present位，而kswapd清除的是Accessed位，不一样
      - task_numa_work是运行在进程调度的过程中插入的一个函数

    - 物理页的nid可能存储在page的flag中（`(PF_POISONED_CHECK(p)->flags >> NODES_PGSHIFT) & NODES_MASK;`）或直接根据page的物理地址去对应节点

- 什么是"NUMA 亲和性（affinity）"？内核如何表示和计算它？
  - NUMA亲和性指进程更容易在哪个节点上运行，从哪个节点分配内存，对应的内核函数是`sched_numa_find_closest()`
  - 内核通过`nodemask_t`或`cpumask_t`，都是用位图来表示，例如`nodemask_t`的bit 0就表示node 0，bit 1就表示node 1，bit为1表示亲和，0表示不亲和

- `numa_node_id()` 返回的是什么？在进程迁移时它会变化吗？
  - 返回的是当前进程所处的节点id
  - 进程迁移的时候可能会发生变化，因为其表示的是当前运行的CPU所处的NUMA节点


**建议验证**：

- 搜索内核源码中 `numa_node_id()` 和 `page_to_nid()` 的使用
- 阅读 `Documentation/admin-guide/mm/numa_memory_policy.rst` 了解内存策略
- 创建一个多线程程序，绑定不同线程到不同 NUMA 节点，测量远端 vs 本地内存访问延迟差异

## 三、NUMA 节点与 ZONE 的层级关系

### 3.1 整体层次结构

**核心概念**：在支持 NUMA 的系统中，内核的内存管理呈现清晰的层级：

```
NUMA Node 0                      NUMA Node 1
  ├── ZONE_DMA                     ├── ZONE_DMA
  ├── ZONE_DMA32                   ├── ZONE_DMA32
  ├── ZONE_NORMAL                  ├── ZONE_NORMAL
  ├── ZONE_MOVABLE                 ├── ZONE_MOVABLE
  └── ZONE_DEVICE                  └── ZONE_DEVICE
       │                                │
       ├── free_area[0..MAX_ORDER]      ├── free_area[0..MAX_ORDER]
       │    ├── 4KB 链表                │    ├── 4KB 链表
       │    ├── 8KB 链表                │    ├── 8KB 链表
       │    └── ...                     │    └── ...
       └── per-CPU pageset             └── per-CPU pageset
```

**学习目标**：

- 理解 "节点 → ZONE → free_area → per-CPU pageset" 的层级关系
- 明确：不同节点的 ZONE_NORMAL 是相互独立的（各自的伙伴系统）
- 理解 `pg_data_t`（节点描述符）结构体的核心成员

**可能必须理解的关键问题**：

- 在 UMA（非 NUMA）系统中，`pg_data_t` 是否存在？有多少个？
  - 非NUMA的系统（UMA）中，pg_data_t只有1个，因为所有CPU都是同一个节点

- 为什么 ZONE 要隶属于节点，而不是跨节点统一管理？
  - 因为内存是隶书于某个节点的，而ZONE只是对内存使用的逻辑划分，所以ZONE也是隶属于节点的
  - 另外， 内核在 `build_zonelists()` 中构建每个节点的 zonelist 时，需要先按节点距离排序，再在同一个距离内按ZONE 类型fallback。如果 ZONE 不属于节点，这个排序就无法实现。
  
- 如果系统只有 2GB 物理内存，还会有 ZONE_HIGHMEM（32 位）或 ZONE_DMA32 吗？
  - 如果系统只有2GB，那会有ZONE_HIGHMEM，因为32位下内核还是只能用1G内存空间，需要HIGHMEM来做不可见地址区域的动态映射
  - 没有ZONE_DMA32，编译时候就决定了（32位下`CONFIG_ZONE_DMA32=n`，而64位下`CONFIG_ZONE_DMA32=y`）


### 3.2 数据结构的对应关系

**学习目标**：

| 概念 | 内核数据结构 | 说明 |
|------|-------------|------|
| NUMA 节点 | `pg_data_t`（别名 `pgdat`） | 每个 NUMA 节点一个实例 |
| 内存区域 | `struct zone` | 隶属于特定 `pg_data_t` |
| 物理页 | `struct page` | 通过 `page_zone()` 可反查所属 zone |
| 伙伴系统 | `zone->free_area[]` | 每个 zone 有独立的伙伴系统 |

**可能必须理解的关键问题**：

- 每个 `struct page` 如何知道自己属于哪个节点、哪个 zone？
  - 每个struct page的信息可以推断属于哪个节点与zone
  - 通过page_to_nid()知道属于哪个节点，内部实现可能是基于page->flags（`PF_POISONED_CHECK(p)->flags >> NODES_PGSHIFT) & NODES_MASK;`）或基于物理地址推断
  - 通过page_zone()知道属于哪个zone，内部实现也是基于page->flags（`(page->flags >> ZONES_PGSHIFT) & ZONES_MASK;`）

- `struct zone` 中维护了哪些水位线（watermark）？如何影响内存分配行为？
  - 维护了HIGH、LOW、MIN三种水位线
  - 之前说的kswapd其实是基于节点以及不同zone来触发的，只检查并回收指定节点对应zone的物理页
  - 但slowpath中也会触发所有节点下zone的kswapd
  - MIN<free<=LOW，唤醒本节点的kswapd异步回收，如果free <= MIN，则fastpath不成功，走flow path，并且会唤醒节点或全局的kswapd

- ZONE 之间是否可以相互借用内存？（提示：fallback 机制）
  - 没有互相借用的说法，只有当首选ZONE内存不足无法申请时，会基于fallback机制，选择zonelist顺序后一位的ZONE继续尝试分配
  - 但有的GFP标志在没有可以fallback的目标，他就会失败，例如GFP_DMA时，如果ZONE_DMA没有可分配内存，则也没法FALLBACK


**建议验证**：

- 阅读 `/proc/zoneinfo` 的输出，理解每列的含义
- 阅读 `/proc/buddyinfo` 的输出，观察不同节点、不同 zone 的空闲内存分布
- 搜索内核源码中 `struct zone` 的定义，找出 `watermark`、`free_area`、`node` 等关键成员

## 四、ZONE 内存区域详解

### 4.1 为什么需要 ZONE 划分？

**核心问题**：既然有伙伴系统管理物理内存，为什么还要将内存分为不同 ZONE？

**答案线索**：硬件限制。不同硬件访问物理内存的能力不同。

### 4.2 各 ZONE 类型详解

| ZONE 类型 | 覆盖的物理地址范围（典型） | 存在的理由 |
|-----------|--------------------------|-----------|
| **ZONE_DMA** | 0 ~ 16MB | 老式 ISA 设备的 DMA 只能访问低 16MB |
| **ZONE_DMA32** | 0 ~ 4GB | 32 位 PCI 设备的 DMA 只能访问低 4GB（64 位系统） |
| **ZONE_NORMAL** | 16MB/4GB ~ 内核直接映射上限 | 内核直接映射（直接映射区）能访问的正常内存 |
| **ZONE_HIGHMEM** | 内核直接映射上限以上（仅 32 位） | 32 位内核虚拟地址空间不足，需要动态映射才能访问 |
| **ZONE_MOVABLE** | 可动态调整 | 用于内存热插拔、巨型页分配、减少碎片 |
| **ZONE_DEVICE** | 设备内存（如 GPU 显存、PMEM） | 支持持久内存、设备直接映射 |

**可能必须理解的关键问题**：

- 为什么 64 位系统通常没有 ZONE_HIGHMEM？32 位为何必须有？
  - 32位必须有的原因是在32位的虚拟内存空间划分中，只有1G的区域划给了内核。而实际物理内存如果大于1G，则区域的范围无法表示所有的物理地址。所以32位的区域中，需要在内核的区域再划一块ZONE_HIGHMEM的ZONE出来，然后用这块区域动态映射超出1G范围的其他物理地址。
  - 而64位系统，内核区域和用户区域是对半分，内核直接映射区的范围远大于当下所有物理内存之和，可以直接涵盖当下所有的物理地址范围，因此就不需要ZONE_HIGHMEM了。

- ZONE_DMA 在现代系统中还有必要存在吗？（提示：某些嵌入式设备、虚拟机）
  - 还是有必要存在的，因为ZONE_DMA本身是为了兼容旧设备使用，这类旧设备的寻址线是24根，因此寻址范围只有0~16MB
  - ZONE_DMA32是的寻址线是32根，因此寻址范围只有0~4GB
  - 因此还需要使用ZONE_DMA或者ZONE_DMA32为其分配内存地址，保证它能正常工作。
  
- ZONE_NORMAL 和 ZONE_DMA32 在 64 位系统上是否会发生重叠？内核如何处理？
  - 不存在重叠，因为64位系统可以表示的物理内存地址范围完全够用，因此是先将0~16MB划分给ZONE_DMA，然后把16MB~4GB的区域划分给ZONE_DMA32，接着再将剩余的划分为ZONE_NORMAL。

- ZONE_MOVABLE 中的"可移动"和内存规整（compaction）中的"MOVABLE 页"是同一个概念吗？
  - 不是一个概念
  - MOVEABLE区域的设计主要是为了解决一下的问题：
    - 大页分配时需要连续内存，可以MOVE整理出来
    - 碎片过多时，可以整理
    - 内存热拔插时，可以将数据安全转移到其他区域
    - NUMA情况下迁移，从0节点的MOVEABLE迁移到1节点的MOVEABLE
  - ZONE_MOVEABLE内的所有页的迁移类型都是
  - 而其他区域中，也存在迁移类型是MIGRATE_MOVABLE的页
  - 内存规整，是指对各个ZONE中迁移类型为MIGRATE_MOVABLE的物理页进行批量移动
  
- ZONE_DEVICE 存放的是什么？为什么 GPU 显存、NVDIMM 需要特殊的 ZONE？
  - ZONE_DEVICE存放的是外部硬件的内存信息
  - GPU等需要特殊ZONE是因为这部分的内存不能被伙伴系统拿去分配，但是CPU又需要可以访问它，并且可以热拔插，所以需要特殊ZONE来表示

### 4.3 ZONE 的水位线与分配策略

**核心概念**：每个 ZONE 维护三个水位线——高（high）、低（low）、最小（min），用于触发内存回收。

**学习目标**：

- 理解 `pages_high`、`pages_low`、`pages_min` 的含义和关系
  - high、low、min都是每个ZONE的内存水位线阈值
  - 其中，high和low是通过min推算出来的，而min的值是直接和全局变量`min_free_kbytes`挂钩
  - 当`min_free_kbytes`被确定后，例如128MB，这个值会被所有ZONE按比例大小分配,这个分配的大小就会换算为物理页数量`pages_min`，例如假设ZONE_NORMAL分配的大小为100MB，那么pages_min就是100MB/4KB = 25000（张）
  - pages_low= pages_min* 5 / 4 （即 pages_min的 125%），pages_high= pages_min* 3 / 2 （即 pages_min的 150%）

  - 会影响内核对内存回收的行为

- 当空闲内存低于 `pages_low` 时，内核如何触发 kswapd 唤醒？
  - 当alloc_pages发现某个ZONE此时空闲内存低于low时，会触发一个异步的kswapd回收,回收当前ZONE的物理内存页

- 当空闲内存低于 `pages_min` 时，分配必须同步回收（direct reclaim），为何这很危险？
  - 递归风险：在同步回收（direct reclaim）过程中，可能会调用注册的 `shrinker`回调（如文件系统缓存回收）。这些回调函数本身**可能再次申请内存**，如果此时内存依然极度紧张，可能形成**递归申请→回收→申请**的死锁或长时间停顿。
  - 性能问题**：direct reclaim 发生在请求内存的**进程上下文**中，该进程会被阻塞，导致**延迟不确定**。如果多个进程同时触发 direct reclaim，系统响应性会急剧下降。**
  - 全局状态恶化：当系统需要频繁进行 direct reclaim 时，说明内存压力已极大，可能触发 OOM Killer 杀死进程，甚至导致系统假死。


**可能必须理解的关键问题**：

- 水位线的值是如何计算出来的？（提示：基于 `min_free_kbytes` 参数，按 zone 大小比例分配）

  - 每个ZONE的水位线都是单独计算的
  - min_free_kbytes是系统全局设置，表示系统必须保留的最小空闲内存（以 KB 为单位）
  - 计算时，内核根据每个 Zone 管理的页面数（`managed_pages`）占所有 Zone 总页面数的比例，将 `min_free_kbytes`换算的页面数分摊到每个 Zone，得到该 Zone 的 `pages_min`。
  - 然后pages_low是125%的pages_min，pages_high是150%的pages_min。

- ZONE 之间的 fallback 分配顺序是怎样的？为什么是这个顺序？

  - fallback分配顺序都记录在`struct zonelist`结构体里

  - Zone 类型顺序：在单个节点内，zonelist 通常按 Zone 类型排序（如 NORMAL -> DMA32 -> DMA）。

  - 节点距离顺序：跨节点时，按 NUMA 距离由近到远排序。

  - 注：内存策略MPOL_BIND / MPOL_PREFERRED可以创建自定义的zonelist，如果没有自定义的则会使用默认的zonelist（内核初始化时构造的）。

    - MPOL_BIND：只会在本节点内尝试分配，失败则返回NULL

    - MPOL_PREFERRED：从某个首选节点开始尝试

      ```
      unsigned long nodemask = (1 << 1);
      mbind(addr, len, MPOL_PREFERRED, &nodemask, MAX_NODES, 0);
      
      [node1.ZONE_NORMAL, node1.ZONE_DMA32, node1.ZONE_DMA,  // 首选节点在前
       node0.ZONE_NORMAL, node0.ZONE_DMA32, ...,            // 然后其他节点
       node2.ZONE_NORMAL, ...]
      ```

- 什么场景下内核会尝试从"远端 NUMA 节点"分配内存？

  - 基于用户程序指定的内存策略，例如interleaving
  - 本地内存不足导致fallback
  - NUMA的负载均衡策略，平衡各个节点之间的负载


**建议验证**：

- 阅读 `mm/page_alloc.c` 中的 `zone_watermark_ok()` 函数

### 4.4 ZONE 的 fallback 机制

**核心概念**：当首选 ZONE 无法满足分配请求时，内核会按预设的 fallback 列表依次尝试其他 ZONE。

**学习目标**：

- 理解 `fallbacks[]` 数组的构建逻辑（在 `build_zonelists()` 中）
- x86_64 的典型 fallback 顺序：`ZONE_NORMAL → ZONE_DMA32 → ZONE_DMA`
- NUMA 场景下，fallback 如何结合节点距离进行排序？

**可能必须理解的关键问题**：

- GFP 标志（如 `GFP_DMA`、`GFP_DMA32`）如何影响 fallback 的路径？

  - 如果设置了GFP_DMA，那么分配内存时只会从ZONE_DMA获取，不会有ZONE_NORMAL等出现在fallback路径上
  - 如果设置了GFP_DMA32，那么分配内存优先从ZONE_DMA32获取，fallback上就只有ZONE_DMA。

- 为什么 fallback 顺序通常是 "通用 ZONE 优先，受限 ZONE 靠后"？反过来会怎样？

  - 因为受限ZONE例如DMA区域内存大小本身就16MB，资源非常宝贵。因此如果可以使用更通用的ZONE则优先使用
  - 如果先尝试受限ZONE，可能导致后续受限ZONE的区域长时间紧张

- 在 NUMA 下，zonelist 的结构是怎样的？（提示：`struct zonelist`、`struct zoneref`）

- 内核中的 `__GFP_THISNODE` 标志是做什么的？什么场景必须使用？

  - 强制内存分配**只在当前 NUMA 节点**进行，不跨节点分配，即使当前节点内存不足导致分配失败。

    当设置此标志时：

    1. **不进行内存回收** - 不会触发直接回收或压缩
    2. **不进行回退** - 不会尝试从其他NUMA节点分配
    3. **严格执行本地分配** - 仅在当前CPU所在的节点分配

  - 硬件绑定场景

    - **设备驱动**：设备DMA只能访问特定节点的内存
    - **NUMA感知硬件**：如某些GPU、网卡、加速卡有节点亲和性要求

  - 性能敏感：

    - 要求一定要使用本节点分配内存
    - 对延迟极其敏感的内核路径，避免NUMA远程访问的开销（远程访问可能慢2-3倍）

  - 内存策略

    - 用户空间通过`mbind()`设置的内存绑定策略 MPOL_BIND

## 五、综合篇：NUMA + ZONE 在关键场景中的表现

### 5.1 伙伴系统分配一页物理内存的完整路径

从调用 `alloc_pages()` 开始，到拿到 `struct page` 结束，完整路径大致为：

1. 确定 GFP 标志和分配策略（preferred node、mempolicy、zonelist）
2. 遍历 zonelist 中的每个 zoneref（node + zone 组合），按 fallback 顺序尝试
3. 在目标 zone 中检查水位线、尝试 fast path（per-CPU pageset）
4. 若 fast path 失败，进入 slow path：
   - 尝试内存规整（compaction）
   - 触发 kswapd 回收
   - 执行直接回收（direct reclaim）
   - 必要时触发 OOM killer
5. 若分配成功，初始化 page 并返回

## 区域

正如我们提到的，内存中的每个区域都由 `struct zone` 描述，它是它所属节点的 `node_zones` 数组的一个元素。`struct zone` 是页面分配器的核心数据结构。 区域表示物理内存范围，并且可能存在空洞。

页面分配器使用 GFP 标志，请参阅 [内存分配控制](https://linuxkernel.org.cn/doc/html/latest/core-api/mm-api.html#mm-api-gfp-flags)，由内存分配指定，以确定节点中内存分配可以从中分配内存的最高区域。 页面分配器首先从该区域分配内存，如果页面分配器无法从该区域分配请求的内存量，它将从节点中的下一个较低区域分配内存，该过程将继续到最低区域（包括最低区域）。 例如，如果一个节点包含 `ZONE_DMA32`、`ZONE_NORMAL` 和 `ZONE_MOVABLE`，并且内存分配的最高区域是 `ZONE_MOVABLE`，则页面分配器从中分配内存的区域顺序为 `ZONE_MOVABLE` > `ZONE_NORMAL` > `ZONE_DMA32`。

在运行时，区域中的空闲页面位于每个 CPU 页面集 (PCP) 或区域的空闲区域中。 每个 CPU 页面集是内核内存管理系统中的一个重要机制。 通过在每个 CPU 上本地处理最频繁的分配和释放，每个 CPU 页面集提高了性能和可扩展性，尤其是在具有多个内核的系统上。 内核中的页面分配器采用两步内存分配策略，首先从每个 CPU 页面集开始，然后回退到伙伴分配器。 页面在每个 CPU 页面集和全局空闲区域（由伙伴分配器管理）之间批量传输。 这最大限度地减少了与全局伙伴分配器频繁交互的开销。

架构特定代码调用 free_area_init() 来初始化区域。
