

# 物理内存管理（下）

参考：Linux 5.10.256  6.19.8

上一章节以回收内存的kswapd内核线程为引，讨论了内核如何区分物理页可以回收，以及对匿名页和文件页的不同处理机制。但这些都是应用程序层面（使用虚拟内存访问）的内存回收，这章节是继续补充内核对自身使用的内存是怎么做分配、回收的。

因此本章节的线索如下：

1. 内核对自身内存的分配管理——slab分配器与shrinker
2. 基于swap延伸的优化机制——zram与zswap

### slab分配器

注：内核从2.6开始就已经使用SLUB作为默认的通用分配器了（但还是支持SLAB与SLOB，可以使用Kconfig更改），SLAB分配器实现代码最终在Linux 6.7被移除。但SLUB本质上脱胎于slab，因此本章节先从slab开始讲。

内核完成伙伴系统初始化后，就可以向伙伴系统申请物理页内存了，但是众所周知的是：伙伴系统分配的单位是物理页，即使是order = 0（最小的0阶）对应的大小也是一页物理页的大小，至少是4KB。

内核里为进程调度创建的一个`task_struct` 结构体大概2KB，为虚拟文件系统创建一个`inode`结构体大概600字节。如果每个对象创建都是直接向伙伴系统申请一页 4KB，那有点太奢侈了。以内核动辄数十万个对象的情况来看，这种狂野的做法根本不可能用的起来。

“内存给我之后，我自己管理是不是也行？”针对这种系统只能选择要么给一大块内存，要么没得申请的情况，相信大部分人的想法都是这样。

但如果放手让每个模块自己去实现，那马上内核这种小内存管理机制马上就会开始百家争鸣，不符合内核“大一统”的一贯风格。因此内核为模块这种小内存对象申请、释放设计了统一的机制，我们通常叫做slab分配器（slab allocator）。

slab分配器并不是说“有一种名叫slab的分配器会给各个模块分配内存”，而是指内核中基于slab对象（`struct slab`）来管理小内存分配的整个机制。它的核心是用`slab`对象来记录和跟踪一块连续内存页的使用情况。但在整个机制中直接与模块打交道的并非slab对象，而是内存缓存（kmem_cache）。

#### 内存缓存

内核缓存（kmem_cache）有两种形态，分别可以称为“通用内存缓存”与“专用内存缓存”。

**通用内存缓存**

通用内存缓存是内核初始化后创建好的一系列的`kmem_cache`结构，区别是支持分配的大小以2的次幂增长（但存在特例，下文会提及），如`kmalloc-8`、`kmalloc-16`、`kmalloc-32`、`kmalloc-64`、`kmalloc-128`……

在内核中，所有通用内存缓存以一个全局数组`kmalloc_caches[type][index]`的形式存在，type指的是内存区域，如NORMAL、DMA等等，这个将会在下一章节解释。而index就是对应不同大小的内存缓存，虽然Linux6.12的代码中index=3对应了`kmalloc-8`，但因为index本质上是通过查表获得，在内核编译设置下，一些缓存可能并不会实际存在，因此并不能简单就认为index的含义是2的几次方。

我们非常熟悉的`kmalloc()`与`kfree()`这两个内存申请接口，实际上正是在向通用内存缓存去申请指定大小的内存。

当模块调用接口申请内存时，接口内部会自动匹配最合适的内存缓存，并触发内存缓存的内存分配行为。例如kmalloc(32)会从`kmalloc-32`的通用内存缓存申请，kmalloc(128)则会从`kmalloc-128`的通用内存缓存申请。

注：如果模块使用kmalloc申请的内存超过某个阈值（例如8KB）时，则接口内部直接改向伙伴系统申请。

注2：内核中有宏规定了最小可申请内存大小`KMALLOC_MIN_SIZE`，假设其定义值为16，那实际上就没有`kmalloc-8`这个通用内存缓存了，申请小于宏定义字节的内存会内部重定向到当前支持的最小通用内存缓存（例如`kmalloc(8)`可能会从`kmalloc-16`分配）。

由于通用内存缓存均是2的次幂大小，则`kmalloc-128`的下一个就是`kmalloc-256`了。假设模块调用`kmalloc(150)`，则为了满足模块需求（总不能让模块少申请一点吧？），接口只能通过`kmalloc-256`分配。分配了256字节而模块只需要150字节，因此就浪费了106字节的空间。以内核数万、数十万对象来看，这种内存浪费问题是涉及到系统可用性的、非常严重的问题。

为了**缓解**这种内存浪费的问题，通用内存缓存引入了几个非2的次幂的缓存，例如`kmalloc-96`、`kmalloc-192`，避免内存分配时，直接从64跳到128、从128直接跳到256，这些都是小对象比较容易命中的区间。因此上文提到的kmalloc(150)就变成由`kmalloc-192`分配，浪费的内存从106字节减少到了42字节，算是效果显著了。

[图片 kmalloc申请通用内存缓存]

对于通用服务来说，要想做到面面俱到事事满意难度过大了，只能缓解并非解决，真要解决就需要模块配合——创建自己的专用内存缓存。

**专用内存缓存**

由于通用内存缓存可返回的内存大小是预设的，因此如果模块不是将自己的结构体严格按照预设来设计，免不了会出现分配多余内存的浪费现象。

“不要让模块适配内存缓存，而是内存缓存来适配模块呢？”

这一思路的结论就是内核提供了专用内存缓存的相关接口：

- `kmem_cache_create`：创建一个专用内存缓存结构，分配的每个对象大小由模块传入
- `kmem_cache_alloc`：通过专用内存缓存结构申请对象
- `kmem_cache_free`：通过专用内存缓存结构回收对象
- `kmem_cache_destroy`：销毁一个专用内存缓存结构

因为结构体大小在定义时就确定了，因此模块就可以为那些在运行时会大量产生的对象创建专用内存缓存用于这类对象的内存管理。

不论是通用内存缓存还是专用内存缓存，都是通过简单的申请、返还接口为模块屏蔽了大量内部的内存管理逻辑。但既然称为“slab分配器”，接下来我们就回过头来讲一下内存缓存基于slab对象，为模块提供内存服务的流程和原理。

#### 基于slab的内存管理

内存缓存结构`kmem_cache`管理自己的slab对象，而slab对象负责管理可分配的对象内存。

`kmem_cache_node`结构体是`kmem_cache`为per-cpu性能优化而设计的每核实际管理slab对象的结构体。

在`kmem_cache_node`中存在3条链表，用于管理不同状态下的slab对象，分别是：

- `slabs_full`：slab对象已满，没有可分配空间
- `slabs_partial`：slab对象部分内存已经分配出去了，且当前仍有可分配的空间
- `slabs_free`：slab对象中的内存均没有分配出去

slab对象的创建与物理页的分配思路一致，遵循着“懒分配”原则——用不到就先不创建。因此不论是通用内存缓存还是专用内存缓存，在`kmem_cache`结构体刚被创建时三条链表都是空的。

当收到模块的内存申请时，内存缓存将会按下面的逻辑处理：

1. 首先尝试从`slabs_partial`链表找一个slab对象分配——先把没用满的先用满

2. 如果`slabs_partial`链表为空，则尝试从`slabs_free`链表找一个slab对象分配——启用后备隐藏能源

3. 如果`slabs_free`也为空，那就申请一个新的slab对象并关联物理页

“slab”的英文可以直译为“块”，在内核里的意义是一个slab对象代表了一块可分配对象的内存，与实际的一至多张连续物理页对应。

接下来就先介绍一下slab对象的主要字段。

**slab对象结构**

接下来要介绍的结构体是`struct slab`吗？不，其实并没有叫这个名字的结构——slab分配器复用了`struct page`结构体来描述slab对象。

在之前的章节介绍过，`struct page`结构是内核中管理物理内存的结构，对应的就是一至多页物理内存页，那这不巧了嘛，slab对象也是要做类似的事，因此slab分配器直接复用了该结构体，并专用的字段以union的形式声明，相关字段如下：

```
struct {	/* slab, slob and slub */
			union {
				struct list_head slab_list;
				......
				};
			};
			struct kmem_cache *slab_cache; /* not slob */
			/* Double-word boundary */
			void *freelist;		/* first free object */
			union {
				void *s_mem;	/* slab: first object */
				unsigned long counters;		/* SLUB */
				struct {			/* SLUB */
					unsigned inuse:16;
					unsigned objects:15;
					unsigned frozen:1;
				};
			};
		};
......
union {		/* This union is 4 bytes in size. */
		......
		unsigned int active;		/* SLAB */
		int units;			/* SLOB */
	};
```

忽略slub使用的结构后，slab的主要字段有：

- slab_list：用于将slab挂在内存缓存的三种链表（`slabs_full`/`slabs_partial`/`slabs_free`）上
- s_mem：指向slab对应的物理页内存的起始地址（第一个对象的地址）
- freelist：指向可用于分配的空闲对象的管理结构，管理结构内部存储了对象的索引
- slab_cache：指向该slab对象对应的`kmem_cache`结构体
- active：对应当前已经分配的对象数量

每当分配/回收一个对象时，都会触发active字段的增加/减少，并且触发内存缓存对slab对象当前状态的检查：

- active等于0：代表没有被分配出去的对象，slab对象会被从当前链摘下并挂到free链上。
- active等于slab最大可分配对象数（记录在`kmem_cache.num`中）：代表没有可分配的对象了，slab对象会被从当前链摘下并挂到full链上。
- 除了上面两种边界场景，slab对象都预期挂在partial链上。

每当需要获取一个新对象时，slab对象就可以从管理结构中获取一个空闲对象的索引。由于对象的大小是已知的，并且s_mem已经告知了第一个对象的地址，那么就可以通过计算地址偏移量从而得到该空闲对象的地址并且返回。

自然的，如果模块释放一个对象内存，slab对象就是把该对象计算出索引并且重新添加到管理结构中即可。

这个申请释放流程往简单的说就是两句话的事，但为了更详细的理解整体逻辑，则本章节需要先回答两个问题：

- slab对应的物理页大小是怎么确定的？
- slab对空闲对象的管理结构是什么样的？

**确定slab的物理页大小**

每个内存缓存结构`kmem_cache`在初始化时，就已经将后续创建slab对象的规则给定了下来，例如：

- slab对象对应几张物理页（`kmem_cache.gfporder`）
- 每个slab对象支持分配多少个对象（`kmem_cache.num`）
- slab如何管理可分配的对象（`kmem_cache.flags`中的标志位）

因此，同一个内存缓存中的每个slab对象大小、行为总是相同的。

从结论上来看，slab的大小由`kmem_cache.gfporder`的值决定，gfporder字段值和伙伴系统的order一致（因为本来就是去找伙伴系统申请物理页），为0表示每个slab对象对应1页物理页，为1则表示每个slab对象对应2页物理页，以此类推。

这个值是怎么确定的呢？对于这点的答案很朴素——gfporder的值是试出来的，内存缓存初始化时基于后续要分配的对象大小，使用for循环从0试到`KMALLOC_MAX_ORDER`，直到找到第一个让其“满意”的值来使用。

何谓“满意”？

- 首先，对内存的利用率要高，空隙内存的大小（没法分配对象）不超过整段内存大小的12.5%）。

- 其次，用于管理对象的内存区域`freelist`如果不分配在slab的物理页中，那分配出的内存不能超过分配对象内存的一半。

- 再者，对于slab可以分配的对象数目也有限制，因为freelist是用1到2个字节来描述每个对象的位置，因此最多只能描述0-65535，因此如果内存大小够分配超过SLAB_OBJ_MAX_NUM个对象那也不要。

- ......

总而言之，内核设置了很多硬性或启发式的判断条件，用于确定一个合适的gfporder取值，减少内存浪费情况。当确定了取值后，整个slab大小就已经确定了。

同时在这个循环尝试的过程中，对于freelist指向区域的存在形式也被纳入了综合考虑范围。

**slab空闲对象管理结构的存在形式**

slab使用数组这一数据结构来维护可分配的空闲对象链表，因此字段得名freelist。

数组用`freelist_idx_t`类型来表示数组元素的类型，`freelist_idx_t`在编译期间通过 `PAGE_SIZE` （物理页的大小）和 `KMALLOC_MIN_SIZE`（分配对象的最小大小） 的关系从而定下是1个字节（unsigned char, uint8_t）还是2个字节（unsigned short, uint16_t），这个长度对于所有slab对象通用。

idx即索引，由于对象大小已知（`kmem_cache.size`），slab的起始内存已知（`page.s_mem`），因此可以只记录对象的索引来描述指定对象的内存。

这也是为啥会存在一个`SLAB_OBJ_MAX_NUM`的宏定义：

```c
#define SLAB_OBJ_MAX_NUM ((1 << sizeof(freelist_idx_t) * BITS_PER_BYTE) - 1)
```

因为数组需要能够描述所有的对象位置，那么对象的数量就不能超过元素类型可以表示的范围。

[图片 freelist示意图]

那这个数组放在哪呢？内核根据“这块内存从哪里来”区分了三种形式，并从代码看选择优先级从高到低是：

- objfreelist-slab
- off-slab
- on-slab

首先要明确一点：**数组的结构是固定的，以上三种讨论的只是数据放哪里的问题。**

我们用一张图来介绍on-slab与off-slab，由于objfreelist-slab比较复杂，因此得要一张长图。

[图片 on-slab与off-slab]

[图片 objfreelist-slab申请、释放示意图]

从图中可以看出，objfreelist-slab巧妙的做法并没有额外浪费内存。用尚未分配的最后一个对象内存先存储分配情况，在最后一个对象也分配出去后，意味着没有free的对象，即freelist可以置为空。此时若有对象被释放，那么freelist就可以继续复用这个对象的内存来维护freelist。但是要采用这种方式有诸多的条件，本文不做赘述。

特意区分不同的存储方式主要也是为了尽可能得用好有限的内存，以on-slab模式来举例，对于4KB的slab可分配内存来说：

- 如果对象大小为512字节，则满打满算可以分配8个对象。此时如果选择把freelist放在物理页中，那相当于挤占了宝贵的对象分配空间，直接导致对象分配个数少了一个，利用率较低。
- 如果对象大小是500字节，则剩下无法分配的96字节又刚好可以用来存储freelist，不用额外申请一块内存来保存freelist，此时利用率就上来了。

那么slab的关键知识点都介绍到了，接下来介绍一下它的两种变体slob与slub。

### slob与slub

slab是最初设计出来的通用分配器，随着Linux系统在各种设备上运行，场景需求也在不断变化，因此对于内存分配方式也需要做相应的适配：

- 针对嵌入式小内存设备，slab分配器不仅代码量多，而且管理结构也很占用宝贵的内存。因此Linux设计了slob通用分配器（Simple List Of Blocks），针对解决slab分配器本身机制的内存使用问题。
- 针对现代计算机越来越大的可用物理内存，slab分配器可以用于分配的内存也越来越大，对分配对象的性能、访问内存的性能要求也越来越高。因此Linux设计了slub通用分配器（Simple List-based Unqueued Buffer）。

这两种变体都对原本slab管理对象的方式做出了改变，本章节将从这一角度进行介绍。其他部分由于涉及到更多没讨论到的知识点，将在以后做串联。

#### slob对空闲对象的管理

slob的管理方案正如其名字所说的Simple与Blocks，其大幅简化了整个内存管理逻辑，不再使用内存缓存与固定大小的slab对象这种“分多个桶”的模式，而是直接做“切蛋糕”，将申请到的物理页按需分割，将新切下的内存块（`slob_block`）分配给申请模块。

Simple体现在多个方面，最直观的就是数据结构简单。

```c
#if PAGE_SIZE <= (32767 * 2)
typedef s16 slobidx_t;
#else
typedef s32 slobidx_t;
#endif

struct slob_block {
	slobidx_t units;
};
typedef struct slob_block slob_t;

/*
 * All partially free slob pages go on these lists.
 */
#define SLOB_BREAK1 256
#define SLOB_BREAK2 1024
static LIST_HEAD(free_slob_small);
static LIST_HEAD(free_slob_medium);
static LIST_HEAD(free_slob_large);
```

短短数行，便已经将slob流程用到的数据结构给声明完毕了。

在`struct page`上，有一个2字节或4字节的`units`字段是slob的专用字段，表示当前物理页上还有多少个单位的空闲内存。由于物理页本身是按`struct slob_block`来分割的，`units`字段的长度也决定了每个内存unit是多大。

需要注意的是`units`指的是空闲内存，而非连续的空闲内存。因此假设物理页空闲的内存分布是`[2个unit空闲 | 1个unit被分配 | 2个unit空闲]`，那么page.units = 4，但此时模块如果要申请3个单位的空闲内存则会失败，因为没有连续的3个空闲unit。

一个单位的内存大小由宏定义控制

```
#define SLOB_UNIT sizeof(slob_t)
#define SLOB_UNITS(size) DIV_ROUND_UP(size, SLOB_UNIT)
```

如果能够理解slob只以一个个unit的内存块来表示、管理内存，则整体流程也很好理解。

当模块申请指定大小的内存时：

1. 将申请大小size与`SLOB_BREAK1`、`SLOB_BREAK2`比较：
   - 小于等于`SLOB_BREAK1`，从`free_slob_small`链表查找
   - 大于`SLOB_BREAK1`小于`SLOB_BREAK2`，从`free_slob_medium`链表查找
   - 大于等于`SLOB_BREAK2`，从`free_slob_large`链表查找
2. 遍历链表上的每一个`strcut page`，若`page.units`小于size则跳过，满足则进一步根据`page.freelist`指向的`struct slob_block`开始寻找满足条件的内存
3. 如果遍历后找到满足条件的内存，则更新对应物理页的units信息（减去刚分配出去的大小）并且更新freelist信息。
4. 如果遍历完毕后也没找到，则申请一页新的物理页，分配这块内存后`page.slab_list`字段挂入该链表

相信整个流程中，只有一个freelist是怎么维护的不明白了，slob中freelist的维护与`struct slob_block`的唯一一个字段units有关。

之所以用一个units就可以完成freelist的维护，是因为slob中有一个约定：

- 如果空闲内存块大小大于1个unit，则第一个unit保存空闲内存块的块数（s[0].units = size），第二个unit保存下一个空闲内存块的偏移量（s[1].units  = offset）。

- 如果空闲内存块大小就是1个unit，则unit的值为负的下一个空闲内存块的偏移量（s[0].units = -offset）

这里的小巧思就在于这个负号，负号隐含了“哦，这是一个1unit大小的空闲内存”的意义，因此内核只需要将值取反即可去检查下一块空闲内存。

[图片 slob空闲内存维护]

整体来说，slob维护了一套简单、粒度较粗的内存管理机制，可是因为物理页每次都被模块切走不定长的内存块，有可能出现大量不连续的小内存，成为内存碎片。

#### slub对空闲对象的管理

要彻底理解通用分配器的行为，实际上还有很多没有学习到的知识点，例如缓存行、内存区域、内存架构等等，这些也是slub做的比slab更好的地方，这些我们将在后续的章节继续讲解，本节主要先讨论slub是怎么实现“空闲对象的管理”的。

slub在`struct page`中不再使用`s_mem`字段，改为使用自己的专用字段`counter`，`counter`内部以位域定义了如下字段：

- inuse：已分配的对象个数
- objects：可用于分配的对象个数
- frozen：表示slub对象被冻结，用于应对多核竞争问题

slub虽然内部区分这三个字段，但对外读写时按`counter`来执行原子操作，保证了这几个字段的一致性。slab需要`s_mem`字段是因为slab依赖freelist中记录的idx计算空闲对象的位置。而slub真正使用了链表的方式将空闲对象使用指针串在了一起，因此只需要freelist指针指向第一个空闲对象即可，不再需要一个基准值来计算偏移量。

那按照这个意思，是不是slub中每个对象都要多分配一个8字节（64位系统）的链表指针用于freelist维护呢？

其实不需要，与slab的objfreelist-slab的思路类似，空闲对象之所以是空闲对象，意思就是没有数据。因此slub分配器就可以先将空闲对象的一部分当做next指针来用。

[图片 slub]

此外，在slub分配器的逻辑中，当page对象完全空闲时会直接释放这页page，而不是想slab分配器那样先挂入到free链表等待后续回收。

关于slub其他更多提升分配综合表现的优化点，我们将在后续章节做callback。

### shrinker

shrinker在内核中指“收缩”的意思，承接上一章节所说，当内核发现空闲内存低于水位线时，除了唤醒kswapd内核线程回收应用程序分配的内存之外，还会想办法回收自己暂时不需要的内存，对应的内核逻辑统称为shrinker。从流程机制上来说就是`模块注册回调函数->内核调用->模块处理`。

**模块注册回调函数**

模块使用 API`register_shrinker`注册自己的shrinker结构体`struct shrinker`，几个主要字段为：

- `count_objects`：回调函数指针，功能是返回估计可回收对象数
- `scan_objects()`：回调函数指针，功能是回收对象并返回实际释放的数量（shrinker中的scan指的都是回收的意思）
- `batch`：模块指定的单次回收最大数量
- `seek`：模块重新创建一个对象难度是多大，如果不懂该填多少的话，内核提供了默认值`DEFAULT_SEEKS`

模块注册成功的shrinker结构体会被挂到全局链表上等待后续调用。

**内核调用**

内核会在两种主要情况下进入shrinker流程：

- 异步：kswapd内核线程运行进入流程
- 同步：直接分配内存时发现内存不足，触发direct reclaim进入流程

在流程函数中，内核会遍历链表上的每一个模块注册的shrinker结构体：

1. 调用模块`count_objects`函数，获取模块估计本次流程可以释放的对象数量，如果模块返回0或`SHRINK_EMPTY`（无可释放），则直接跳过
2. 由于存在回收数量上限（`batch`），因此内核会获取上一次流程剩余没回收的配额（`nr_deferred`）一并算入本次
3. 重复调用模块`scan_objects`函数，直到达到本次流程的回收目标或模块返回`SHRINK_STOP`（不再继续）为止
4. 将本轮没用完的回收配合存入`nr_deferred`，到下次继续使用

由于内存与NUMA、per-cpu等知识点息息相关，涉及到这些的我们日后再谈。

这里先解决几个能当场解答的问题：

- `count_objects`返回0和返回`SHRINK_EMPTY`有什么区别？
- 为什么`scan_objects`需要重复调用？

针对问题一：虽然0和`SHRINK_EMPTY`都代表这次估计没对象可以释放，但在语义上存在区别。如果模块返回`SHRINK_EMPTY`，是很确定的告知内核“本次没有要释放的对象”，则内核可以非常干脆的跳过。而如果返回0，则内核可以认为是“当前无法确定可以回收的数量”或“这次先跳过我”。返回值的不同会影响内核的态度和行为。

针对问题二：上面有提到，shrinker流程可能发生在多种场景下，包括不可睡眠的场景，但不论是哪种其实都要求函数执行尽可能的快。因此在scan时，内核会根据模块的`batch`赋值分多次执行多轮的`scan_objects()`，每轮结束后都会在循环的末尾调用`cond_resched`主动出让CPU让别的内核线程可以先做调度。如果要求模块一次性回收大量对象，那消耗在scan函数的时间就会过长，导致调度不及时影响系统整体运行效率。

**模块处理**

流程中模块处理的部分，属于每个模块内部的独特逻辑，因此不再过多赘述。

在内核模块开发中如果要使用shrinker有几个点要注意：

1. 同步异步的竞争问题：多线程并行会导致临界资源竞争问题
2. 运行上下文不同的问题：kswapd内核线程是可中断、可睡眠的普通内核线程，锁拿不到那就等一下，也还说得过去。而同步调用的情况很有可能是不可睡眠的上下文，取决于调用者申请内存时传入的`gfp_mask`，如果是无法睡眠的情况，回调函数中遇到了锁等待，那问题就大了。

注：目前显式注册了shrinker逻辑的模块可以通过搜索注册函数确认。不得不提的是，基于Linux 5.10.256版本的代码，上面讲了半天的slab/slub/slob分配器，实际上没有和shrinker流程没有直接关系……而是对外封装提供了`kmem_cache_shrink()`函数给有缘人自行调用。

### zram与zswap

上一章节我们谈到了内存回收的主要手段之一的swap机制——在内存和块设备之间将数据搬来搬去。这样做确实效果显著，只是有一个明显的问题：搬运需要涉及I/O，而I/O的速度和内存读写是数量级之间的差距。为此，swap中也补充了cache机制来减少冗余的I/O请求，但I/O总是不可避免的。

因此基于swap的I/O问题的改进方案就接踵而至，我们这里将讨论zram，然后再讨论zswap。

**zram**

如果说swap的思路是内存置换，那么zram的思路就是内存压缩。

众所周知，压缩（zip）指将“数据量大的内容通过可逆的算法处理为较小的数据”，例如“AAAAA”可以用“5A”来表示的话，数据量就从5个字节压缩到了2个字节，压缩率为60%。

而内存压缩（zram）也是一样的道理，如果可以将4KB的物理页数据压缩成1KB呢？那岂不是就可以用1张物理页暂存4张物理页的数据，直接省下了3张物理页的内存，并且还不需要I/O。
