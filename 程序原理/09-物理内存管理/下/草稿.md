





那么申请的物理页是多大呢？slab对象对应的物理页页数通常是2的次幂，例如1、2、4、8……原因也非常好理解，因为伙伴系统本身也是以order在组织内存，所以每次申请时，只能是按order阶数来批量申请物理页。而申请多少页则是由`kmem_cache`的`gfporder`字段决定，字段值通过要分配的对象大小计算而来。

当成功申请到物理页后，slab对象会将整块内存按约定的指定大小进行分割，用于后续模块的内存申请。

例如内存缓存`kmalloc-32`新创建了一个slab对象，关联了一张4KB的物理页，则按照32字节进行分割后，这个slab对象就可以支持分配128个32字节的对象。

按物理页大小除以对象大小算出来的可分配对象个数，实际上是**最大值**。为何说是最大值呢？不是算出来是几个就是几个嘛？这里有一个可能忽略的点：slab对象也需要存储例如内存大小、分配对象情况等管理信息——这些都得占用一部分内存。







针对slab对象的管理信息如何存储，这里有两种方式：

- on-slab：称之为内嵌式，管理信息是存在slab对象对应的物理页中，目的是不占用额外的空间。
- off-slab：称之为外置式，管理信息是存在slab对象结构体上，目的是让物理页完全用于对象分配。

```
    if (set_objfreelist_slab_cache(cachep, size, flags)) {
		flags |= CFLGS_OBJFREELIST_SLAB;
		goto done;
	}

	if (set_off_slab_cache(cachep, size, flags)) {
		flags |= CFLGS_OFF_SLAB;
		goto done;
	}

	if (set_on_slab_cache(cachep, size, flags))
		goto done;
```

判断的标准是：如果内存缓存对应分配的对象大小大于等于物理页大小的八分之一，则采用off-slab模式，反之则是on-slab。

为什么要特意区分不同的存储方式呢？其实考虑的是内存利用率的问题，对于一张4KB的物理页来说，如果要分配的对象大小为512字节，则满打满算只能分配8个对象。而此时如果把slab对象的管理信息也存储在物理页中，那相当于挤占了宝贵的对象分配空间，导致对象分配个数少了一个，利用率较低。而如果要分配的对象大小较小，例如16字节，则一页可以分配256个对象，被挤占少分配十几个那都不是事情，利用率还算高。

那么slab对象中都有哪些信息用于记录对象的分配情况呢？先从slab对象的结构体看起。







对于上文说的on-slab和off-slab的场景，影响的就是freelist指针指向的区域。

freelist字段名看起来是一个list，乍一看似乎是使用`stuct list_head`连来连去，但实际上是一个数组，使用数组下标的方式来维护链表。通过配合起始地址（s_mem）和每个对象大小就可以基于索引计算出空闲对象的内存起始地址。

在on-slab场景中，freelist指针指向的是物理页中的指定区域。而off-slab的场景，则指向内存缓存申请一块独立内存区域。

在on-slab中又能分出多种方式来保存freelist：

- 用物理页的末尾剩余空间来存储
- 用最后一个可分配的对象的内存来存储







那分散到每个对象中存储是什么意思呢？既然freelist是用来存储空闲对象的数组链表，每个元素占用最多两个字节。那如果把每个对象的大小增加一到两个字节，那不就可以把这个freelist平均到每个对象里，不用特意用一块空间存储了？这就是第三种方式的逻辑。

当采用第三种方式时，slab可以分配的数量就不是按分配对象大小来计算了，而是如下公式：

```
slab可分配对象数量num = 物理页大小 / (分配对象大小 + sizeof(freelist_idx_t));
```

这也是当前主流的SLUB分配器的方案，将链表结构分散到每个对象中存储。

通过对freelist的介绍，对象的分配、释放流程相信也不必再提了。在物理页分割对象这一块实际上还有很多细节内容没有讲到，例如slab确实没有单纯只按模块传入的对象大小来切分物理页，而是会在前后多增加几个字节用于支持内存改写检查、记录最后使用者等功能，后续将单开章节来细究。
